# 0002 · 补全 L2/L3，但先定死语义边界

- 日期：2026-08-23
- 状态：已采纳（分阶段实施）
- 相关：[`design/4x4-memory.md`](../design/4x4-memory.md) §1、`plugin-architecture.md` §12

## 背景

4×4 是本插件的基底，L2/L3 不可省略。但项目史上 v2.3 曾预设 L2/L3 两个派生
粒度，并在评审中被砍，原因**不是**"没必要"，而是**从未定义二者的语义差异**
——两个粒度成了未经验证的假设，规范里占了 40% 篇幅却无指标证明其必要。

当前的 `derived=1` rollup 既不是 L2 也不是 L3：它解决的是**注入超预算**，
而 L2/L3 解决的是**语境恢复**。把它当作二者之一会让差距被掩盖。

## 决定

补全 L2/L3，但**先定死判定边界再写代码**：

| | L2 Scenario | L3 Core/Persona |
|---|---|---|
| 作用域 | 单仓、一个主题 | 跨仓、全局一份 |
| 数量 | 每仓多块 | 每用户恰一块 |
| 失效 | 成员 L1 变化即失效 | 长期趋势变化才重建 |
| 存储 | repo 库 | `global.sqlite` |

场景切分：**按会话主题由 LLM 在重建时聚类**，产出稳定 `scenario_key`。
一个 L1 原子最多属一个场景。

## 理由

- **作用域 + 数量 + 失效条件**三者合起来是可判定的，不再是"两个粒度"的
  含糊说法。任何一条记忆都能被明确归到 L2 或 L3。
- 选主题聚类而非按子路径：跨模块的工作流场景无法用路径表达。代价是边界由
  模型判定，故限定**只在重建时聚类**，读路径仍是一条 SQL。
- **禁止多属**：允许一个原子属多个场景，会把失效从"一条规则"变成图传播
  问题——那正是 D9 刚刚消灭的那类复杂度。

## 前置条件

L2/L3 的失效**必须**沿用 D9 的 schema 触发器，不得新增"记得调用失效"的
代码路径。本项目已有三次该模式的事故（D7–D9）。

## 替代方案

- *继续用单一 rollup 冒充 L2/L3*：掩盖差距，且它按预算触发而非按场景组织，
  无法回答"快速恢复一个工作场景"。
- *按仓库子路径切分场景*：边界客观、零 LLM 成本，但跨模块场景无法表达。
  留作 L2 聚类不稳定时的回退方案。
