## 一、事实：写路径用字符结算，消费它的容器用 token 结算

ADR 0007 把派生层的**长度**约束落到了写路径上，这一步是对的——它消除了
「target 只是提示词里的一句请求」这个缺陷。但它落下去的单位是**字符**：

```
pipeline/rebuild.ts  parseScenarios: body.trim().slice(0, ROLLUP_TARGET_CHARS)   // 620
pipeline/rebuild.ts  parsePersona:   body.trim().slice(0, PERSONA_TARGET_CHARS)  // 600
```

而真正花掉这些行的容器，按**渲染后 token** 结算：

```
recall/render.ts  withinBudget: estimateTokens(renderEntry(hit, withId)) > budget -> skip
recall/render.ts  renderEntry:  ....replaceAll('\n', '\n  ')   // 每个换行 +2 字符
```

`renderEntry` 把 body 里每个 `\n` 缩进两格，所以**每一个换行都要花掉字符上限
看不见的 2 个字符**。写入侧与消费侧因此在两个不同的单位里工作，而且是同一条
数据链路上前后相邻的两步。

### 两个已实测的后果

**后果 A：合规画像被整条丢弃。** `withinBudget` 对超预算行的语义是 **skip 而非
truncate**，所以画像没有「变短」这个中间态：

```
cap = worstPersonaTokens() = 171
600 字符（写路径完全放行）+ 21 个换行 -> 172 tok > 171 -> 注入 0 条
线上真实画像 600 chars / 4 nl / 163 tok，余量仅 8 tok
```

即：一条**完全通过写路径校验**的画像，会在每一个仓库里静默消失。线上那条只靠
8 tok 的偶然余量活着。

**后果 B：ADR 0007「残余敞口」段的因果方向写反了，两个分支都假。**
该段声称「先垮的是画像，不是场景块，故本 ADR 要保护的 L2 仍是 6/6」。实测
（固定一个真实形态的合规画像 600 chars / 4 nl / 163 tok，只改场景块密度）：

```
lineLen=30 -> 画像 KEPT, L2 6/6
lineLen=10 -> 画像 KEPT, L2 5/6   <- 声称受保护的 L2 先垮
lineLen= 3 -> 画像 KEPT, L2 4/6
lineLen= 2 -> 画像 KEPT, L2 3/6
```

画像每一次都活了下来；**先垮的恰是它声称受保护的那一层**。两侧并没有谁替谁挡
伤害——画像密时画像整条消失，场景块密时场景块逐条掉，各自沿各自的方向失败。
更正已写回 ADR 0007 原处（原文保留）。

**这两条都不是「守卫没覆盖」，而是「守卫覆盖的是另一个量」**：守卫按最坏形状
定价、算出字符上限，写路径再按字符裁剪——**上限是用 token 解出来的，执行却是
用字符做的**，中间那一步换算只在「密度不超过 `DERIVED_WORST_LINE_CHARS`」时
成立，而没有任何机制保证这个前提。

## 二、决策：把写入侧的单位换成渲染后 token，两侧共用同一把尺子

ADR 0009 的规则反过来说一遍就是本文的决策：**最外面那把尺子是唯一有权结算的
尺子，写路径不许自带一把。**

```
parseScenarios: truncatedToBudget({...}, SCENARIO_MAX_TOKENS)   // 188
parsePersona:   truncatedToBudget({...}, PERSONA_MAX_TOKENS)    // 171
```

复用 `recall/render.ts` 已有的 `truncatedToBudget`（按 token 二分、按**码点**
切分、带可见标记），**不新写截断逻辑**——新写一份就是 D8 所禁止的「同一条规则
的第二个实现」，而且这两份必然在换行定价上再次分叉，正是本文要修的那个缺陷。

**两个执行点必须同轮改完**（ADR 0007 教训 6）。本轮的变异测试复现了这条教训：
只改 `parseScenarios` 时 L3 测试红、L2 测试绿；只改 `parsePersona` 时反之。
任何一半单独上线，另一半继续用容器不结算的单位写库。

### 上限是解出来的，不是拍的

```
PERSONA_MAX_TOKENS  = 171   // 画像在不等式中的份额，按真实 renderEntry 定价
SCENARIO_MAX_TOKENS = 188   // = floor((1300 - 171) / 6)

闭合：171 + 6 x 188 = 1299 <= 1300      余 1 tok
反证：171 + 6 x 189 = 1305 >  1300      超 5 tok（加载期抛错）
```

**只剩 1 tok 是有意为之，不是「差点没算够」。** 步长是
`ROLLUP_MAX_SCENARIOS = 6`，所以最后一个可行值必然落在预算 6 tok 以内，188 就是
最大的那个。**不要为了「留点余量」退到 187**——那等于白送 6 tok 的简报长度给
没有任何占用者的空档。真正的安全边距由下面第 2 条守卫提供：它保证**常规输出
落在上限以下**，而不是让上限本身留白。

## 三、加载期三条守卫，缺一不可

| # | 类型 | 断言 | 防止 |
|---|------|------|------|
| 1 | 容量式 | `PERSONA_MAX + 6 x SCENARIO_MAX <= INJECT_BODY_BUDGET_TOKENS` | 上限之和超预算 |
| 2 | 可满足式 | `worstShapedBody(目标字符数)` 经真实 `renderEntry` 定价 `<= 上限` | 目标字符数脱离守卫；截断沦为常态 |
| 3 | 下界式 | `RECALL_FOREIGN_BUDGET_TOKENS >= 最坏可存储 L2 行的 recall 定价` | 组内成员一条也返回不了 |

> **三条都是不等式，因而各自只在一个方向上约束**——这一点必须写明，否则下一个人
> 会以为「加载期守卫钉住了上限」。以 `PERSONA_MAX_TOKENS` 为例实测：
>
> ```
> 170 -> THREW（守卫 2：请求装不进上限）
> 171 -> 出厂值
> 172 -> LOADS OK   <-- 唯一盲区
> 173 -> THREW（守卫 1：容量允许 P <= 1300 - 6*188 = 172）
> ```
>
> 即**恰好一个错值（172）同时满足两条守卫**。真正把上限钉在「等于最坏形状定价」
> 的，是 `test/pipeline-e2e.test.mjs` 里那条**等式**断言（实测把 171 改成 172，
> 231 条中 2 条变红）。
>
> **不要试图把守卫 2 的 `>` 改成 `!==` 来消除这个盲区**——实测出厂构建**当场
> 抛错**：L2 的请求定价 183 是**有意**低于上限 188 的（这正是「截断是异常路径」
> 的设计），等式守卫会把这段有意的间距判成错误。**间距属于 L2，等式属于 L3，
> 二者不能用同一条断言表达**；等式因此留在测试里。

**第 2 条是本轮新增的，也是最容易被误删的一条。** 直觉上「写入既然按 token 约束
了，字符目标就没用了」——错。`prompts.ts` 仍然必须向模型插值**字符**目标（模型
不会算我们的 token，这是正确分工），所以 `ROLLUP_TARGET_CHARS` 依然是一个真实的
请求参数；一旦把执行改成 token，这个常量就**彻底脱离了所有守卫**。实测（把守卫
2 删掉后逐个探针）：

```
今天（三条守卫齐全）:   ROLLUP_TARGET_CHARS=640 -> THROW，且信息指向派生层
删掉守卫 2 之后:        640 -> NO THROW
                        700 -> NO THROW
                        900 -> NO THROW      <- 连历史缺陷值都无人拦截
```

> 注：ADR 评审稿预计 700/900 会被守卫 3（`RECALL_FOREIGN_BUDGET_TOKENS`）误接住、
> 报出牛头不对马嘴的原因。**实际比预计更糟**：本轮守卫 3 改为对「**裁剪后**的行」
> 定价，因而不再随 `ROLLUP_TARGET_CHARS` 变化，**连那个误接也没有了**。守卫 2
> 是该常量唯一的看守人。

守卫 2 的第二个作用是**让截断保持为异常路径**：`TRUNCATION_MARK` 自身要花
**10 tok / 38 字符**，全部从同一个 188 里出。若常规输出天天触发截断，等于每一个
块都拿真实简报长度去换一句「这里被截断了」。实测边界：

```
620@1/30 = 183 <= 188  ✅        640@1/30 = 189 > 188  ❌ fire
620@1/22 = 187 <= 188  ✅        620@1/10 = 204 > 188  ❌ fire
```

这条断言**同时**绑住字符目标、绑住渲染形状，并且仍然**通过真实 `renderEntry`
定价**——不是 `9 + title + 2 + body` 这类手算（那个前缀依赖 `kind`，L3 的
`- [preference] ` 是 15 字符而 L2 的 `- [fact] ` 是 9 字符，ADR 0007 记录它被
手算错过两次）。

### `DERIVED_WORST_LINE_CHARS` / `worstShapedBody` 换了角色，没有删

它们不再**计算上限**（上限现在是解出来的常量），而是**证明请求可满足**。
「删掉它们」是本轮明确否决的方案：删掉即守卫 2 消失，后果见上表。

### 守卫 3 必须重新求解

旧定义「最坏 L2 行 = `worstShapedBody(ROLLUP_TARGET_CHARS)`」是**字符上限**下的
最坏行。写路径不再按字符约束，该形状就不再是可存储集合的边界了。新问题是：

> **注入侧 ≤188 tok 的所有 body 中，recall 侧最贵的那个是哪一个？**

两条路径对同一 body 定价不同（注入渲染 `- [fact] {title}: {body}`，11 字符外壳；
recall 另加 id 与 `(from …)` 标签，125 字符外壳；两者都按 +2/换行），因此这是个
真问题而非等比缩放。对 (title 长度, body 长度, 换行数) 穷举：

```
最坏行：title=0, body=247 全换行 -> 注入 752 字符 = 188 tok
                                    recall 866 字符 = 217 tok
worstForeignRowTokens = 217（旧值 212），预算 220，余量 8 -> 3 tok
```

**这 3 tok 必须写进注释。** `RECALL_FOREIGN_BUDGET_TOKENS` 的历史是被**渲染形状
变化**顶回来过两次（先加 id，再加 `(from …)` 标签），而不是被任何数字调整顶回来的；
3 tok 大约就是再来一次这种变化的余量。守卫抛错而非告警，所以下一次会在加载期
暴露；注释的作用是让读到那条错误的人知道**当时的余量是 3 而不是一个未知的舒适值**。

### 最外层容器的余量：48 tok，且加载期无人看守

上面三条守卫花的都是 `INJECT_BODY_BUDGET_TOKENS = 1300`，但那是**内部 body
配额**，不是最外面那把尺子。spec §4.2 的真实容器是 **header + body ≤ 1400**。
按最坏合规派生层实测整串 packet：

```
逐条 ceil 求和              1299
整串 renderFramed 后 ceil   1352   （差 53，主要来自 header 51 tok + join 换行）
spec §4.2 容器              1400   -> 余量 48
对照 HEAD（旧上限 183）     1320   -> 余量 80
```

**1352 是紧确界，但复现它需要构造条件**——这一条必须写下来，否则复核者会以为
算错了。取到 1352 要求**每条 entry 恰好顶满 `4 × 上限` 字符**：

```
persona entry   684 字符 (= 4 × 171)
scenario entry  752 字符 (= 4 × 188) × 6
framing header  203 字符
join 换行         8 个   （header 后空行 1 + 条目间 6 + 空行与首条间 1）
                -----
                5407 字符 = ceil(5407/4) = 1352 tok
```

用「饱和式 body」等另一种同样合规的最坏形状只会得到 **1351**（差 1），因为它没
顶到 `4 × 上限` 的边界。**1351 不是算错，是没取到上确界。**

即本轮把上限从 183 提到 188，**有意花掉了 32 tok** 的最外层余量。这是**知情的
取舍**而非疏漏：那 32 tok 换来的是每块简报多约 130 字符，而 1400 这把尺子今天
由三处既有测试守着（`test/inject.test.mjs:317`、`test/layers.test.mjs:1329/1452`），
加载期没有对应守卫。

**逐条求和 1299 与整串 1352 是两个量，不要把差值当成算错**：`withinBudget` 逐条
扣减，每条各自 `ceil` 一次；整串只 `ceil` 一次却要加上 header 和拼接换行。守卫
花的是前者（因为运行时就是那样扣的），最外层容器量的是后者。已登记为待办
（STATUS v0.4.4 结项节待办 d），判据是：**上调任一上限前先复算这个 1352**。

## 四、存量数据：不写迁移脚本

16 条现存派生行（8 个 repo 库 + global 库）中 3 条超新上限
（226 / 238 / 200 tok，全部在 `3e857510e628`），而这 3 条**本来就超今天的
620 字符上限**——它们是 target 强制之前的遗留。新约束比旧约束**更宽**。

收敛判据只需一条：**唯一持有超限行的 `3e857510e628`，其 `packetOverflows`
为 true**，故下一次 rebuild 会 `DELETE` 后重写它的全部块，**自然收敛**。
按生产函数复核（2026-09-08，8 个 repo 库，`ROLLUP_SOURCE_LIMIT=200`）：

```
3e857510e628 3007 true    5ed2b4d261b2 3291 true
ec2636fc223e 1808 true    edf7a6862dde 1916 true
2631a1750495    0 false   7048f15b812d    0 false
94394b03d790 1079 false   aafbf0fa40dd  127 false      （预算 1300）
```

> ⚠️ **本文初稿此处写「9 个库全部为真（含 26592、9545 等）」，那个数是错的。**
> 错因：取数时**手写了一段等价 SQL**而没有调用生产的 `packetOverflows` /
> `queryInjectableSet`，漏掉了 `provenance IN (…)` 过滤，把不可注入的行也计了价。
> **结论不变且更紧**（需要收敛的那个库恰在 true 之列），但这是 ADR 0009 教训 7
> 「绕过真实读者/写者的测量只验证自己的假设」在**文档取数**上的同型复现——
> 本文自己在 §五 教训 3 里讲「旧守卫不会因为曾经有效就继续有效」，
> 同一份文档的取数环节就犯了近亲错误。复核请用生产函数。

写一次性迁移脚本等于新增一个只跑一次的写者——多一个绕过真实写路径的写入口，
正是 D7–D9 要消除的东西。

## 五、教训

1. **「已经把约束落到写路径上」不等于「约束住了容器花掉的那个量」。**
   ADR 0007 做对了「从请求变成强制」，做错了「用哪个单位强制」。修复一个口径
   问题时最容易在相邻的一步引入另一个口径问题（ADR 0009 教训 6 的第三个实例）。
2. **skip 语义会把「超一点点」放大成「全没有」。** 172 vs 171 差 1 tok，
   产品行为是画像**整条消失**。当消费侧是 skip 而非 truncate 时，写入侧任何
   微小的越界都不是「略微超支」，而是全损——**写入侧的精度要求由消费侧的
   失败模式决定**。
3. **改了执行单位，就要重新问一遍「原来那些守卫现在还看着谁」。**
   本轮真正的风险不是新上限算错，而是 `ROLLUP_TARGET_CHARS` 在换单位之后
   **静默失去看守**。删守卫 2 后连 900 都不再抛错——**旧守卫不会因为它曾经
   有效就继续有效。**
4. **最坏情况的定义随约束条件改变，必须重解而不是重新缩放。**
   守卫 3 的「最坏行」在字符约束下和 token 约束下是**两个不同的字符串**
   （620 字符最坏形状 vs 247 全换行）。沿用旧形状会给出 212，低估 5 tok，
   而它的作用恰恰是**下界**——低估的下界不拦任何东西。
5. **成对的修复，任何一半单独上线都会退化**（ADR 0007 教训 6 的复现）。
   本轮用变异测试把这条教训固化成了两条独立的测试：还原任一执行点，
   有且只有对应那一条变红。
6. **一个标记字符串一旦被持久化，它的措辞就变成了数据的一部分。**
   `TRUNCATION_MARK` 原文是「truncated to fit the **recall** budget」，而派生路径
   剪的是 **injection** budget——措辞是字面错误，且会被写进 SQLite、每轮发给模型。
   中性化即可（一处定义两处复用），**不要按预算各造一个标记**：那是同一个字符串
   写两遍。补记：这条**最初没有被任何测试抓住**——把措辞改回去，231 个测试全绿，
   是变异验证发现的缺口，随后才补了测试。
   **「必改项」不等于「已被守住」，两者之间隔着一次变异验证。**

   再补记（QA 阶段）：那条补上的测试，最初被描述为「按性质断言（不得点名任一
   容器）」——**这个描述不准确**。它是**黑名单**：把措辞改成
   `"context packet budget"`（同样点名单一容器）时 231 仍全绿。词表已扩到本仓
   可达的全部容器名并已能打红该反例，但它**仍然是词表**。
   **「措辞是否点名了容器」没有可靠的机器判据**——任何谓词都是一张词表假装成
   性质。诚实的做法是保留黑名单并在注释里写清局限，而不是给它一个更好听的名字。
   **给断言起名时，名字要描述它实际检查的东西，不是它想检查的东西。**
7. **改了写者，就要问「它的产物流向谁」——包括流回自己。**（本轮**未闭合**的
   风险，登记于 STATUS 待办 f。）截断标记现在会持久化，而带标记的 body 会作为
   下一轮 rollup / persona 的**输入回流给模型**（`runPersonaJob` 把
   `current?.body` 喂回提示词）。由此产生三个已复现的征兆：标记**可被伪造**
   （未截断的 body 只要以标记结尾，`endsWith` 即为真，故该谓词不可用于生产
   判断）、裁剪可留下**半截标记 + 真标记**的尾巴、以及**没有任何测试**覆盖
   「带标记的 body 作为下一轮输入」这条闭环。
   这是 ADR 0009 教训 7 的形状：**新写者的产物成了老读者的输入，中间没人量过。**
   （已实测的安慰：不会无限累积——反复重裁同一条 body 稳定在 1 个标记，
   因为 `truncatedToBudget` 先判整体是否合规，合规即原样返回。）

## 六、本文自身被更正过的两处（保留痕迹）

本文初稿有两处论证在 QA 阶段被实测推翻，**均已在正文原处更正并标注**。列在这里
是因为它们的**错误形状**比结论更有价值：

1. **`packetOverflows` 的取数**（见 §四）：手写等价 SQL 漏掉 `provenance IN (…)`
   过滤 —— 绕过真实读者的测量。
2. **`packetOverflows` 的「冻结危害」论证**（`pipeline/rebuild.ts` 注释，本轮已
   重写）：初稿沿用了旧注释里「首轮 rollup 会是此库最后一轮，全靠两个逃生口
   续命」的说法，并据此说明「关闭其中一个逃生口是安全的」。**实测这个危害根本
   不存在**——该触发器计价的是 **raw 集**，而 rollup 的
   `DELETE ... WHERE derived != RAW` **不删 raw 行**：

   ```
   rollup 前  raw 集 4670 tok -> true
   rollup 后  派生 6 行 / 注入 1038 tok；raw 仍 60 行、仍 4670 tok -> 仍 true
   ```

   **两处错误同型**：都在**对着错误的容器推理**——恰恰是本 ADR 要修的那个缺陷
   的形状。缺陷本身是「写入侧用字符、消费侧用 token」，这两处是「注释/取数
   针对的容器，不是代码针对的容器」。**修容器错配的过程中，三次踩进容器错配。**
