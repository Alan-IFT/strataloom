## 背景：一次三轮都没打中根因的修复

起因是真实库里 L2 场景块进不了注入包。前后走了三轮（方案审查 → 执行 → 代码审查），
每一轮都推翻上一轮的诊断，值得逐层记下来——**这三次误判是同一个方法论错误的三种形态**。

| 轮次 | 当时的诊断 | 被什么推翻 |
|---|---|---|
| 1 | 「文档的实测样本过时，真实语料块体更大」 | 算术：6 块 × 243 tok = 1458 > 1300，与语料无关，是常量矛盾 |
| 2 | 「`ROLLUP_MAX_SCENARIOS` 与 `ROLLUP_TARGET_CHARS` 算术矛盾，收窄 target 即可」 | 全仓 grep：`ROLLUP_TARGET_CHARS` **只存在于提示词字符串里**，写路径切的是 `BODY_MAX_CHARS`(2000)，改它等于零 |
| 3 | 「让 target 真正被强制，再补一条加载期守卫」 | 真实库端到端模拟：修复前后 **L2 进包数都是 0/6**，产品行为一字未变 |

第三轮的修复通过了 159 个测试、加载期守卫绿灯，**而它保护的容器不是运行时的那个容器**。

## 真正的根因

`buildContextProvider`（`src/recall/inject.ts`）把两个库的行拼成一个数组，
走**一次** `renderFramed`、**一个** 1300 预算：

```ts
const hits = [
  ...(personal === undefined ? [] : queryInjectionRows(personal)),
  ...(repo === undefined ? [] : queryInjectionRows(repo)),
]
const packet = renderFramed(hits, INJECT_BODY_BUDGET_TOKENS)
```

而 `queryInjectionRows`（`src/store/fts.ts`）有一条**回退分支**：无派生行时取
`INJECT_TOP_N`(20) 条 L1 原子。于是当 global 库尚未生成 L3 画像时，它注入的不是
一条 161 tok 的画像，而是**多达 20 条原子记忆**。

实测（2026-08-29，全部 8 个真实库）：

```
global 库：派生行 0，回退取 7 行，合计 1896 tok
  395 tok | Verify a constant is ENFORCED before treating it as the lever
  378 tok | Dead-letter must end the attempt, not veto the work
  335 tok | 用 source.kind 而非 form 判定消息来源
  313 tok | 中文检索用 CJK bigram 索引，不要用 trigram
  309 tok | 装不上新版先看 stderr：可能是沙箱 EACCES
   93 tok | 遵循「少就是多、删除优于完善」的工程取舍
   73 tok | 产出语言：面向人的用中文

端到端（global 在前、repo 在后，共用 1300）：
  修复前（body 原样）：global 进 5/7 行，L2 进 0/6 块，余 95 tok
  修复后（body 裁 650）：global 进 5/7 行，L2 进 0/6 块，余 95 tok
```

**personal 侧 5 条记忆吃掉 1205 tok，repo 侧的派生层一块都进不来。**
加载期守卫假设 personal 只花 161 tok，**低估 1735 tok——比整个预算还多**。

顺带证伪两个此前被当作事实引用的数字：

- 「6 块进 3 块」：repo 库**单独**看是 **4/6**；「3」是混入 global 侧后的观测，
  却被归因成「repo 块太胖」——**归因错了，真正吃预算的是 global 侧**；
- 「真实块换行密度 1.6/千字」：那是**单库采样**（`edf7a686`），
  跨全部真实库最大是 **11.94/千字**，差 7 倍。

## 为什么加载期守卫这条路走不通

守卫要断言的是「派生层装得进预算」，但预算的实际占用由**运行时才知道的两件事**决定：

1. global 库此刻有没有 L3 画像（有则 161 tok，无则回退到最多 20 条 L1）；
2. 那些 L1 原子各自多长（本身只受 `BODY_MAX_CHARS`=2000 约束，无注入侧上限）。

即 `INJECT_TOP_N × BODY_MAX_CHARS` 这个组合**完全不受任何加载期断言约束**。
一条加载期常量断言无法覆盖一个内容依赖的运行时构成——
**这不是守卫写得不好，是守卫这个手段与问题不匹配。**

## 业界调研：hermes-agent 的做法

调研了两个项目，只有一个可比。

### hermes-agent —— 按来源切分预算，且在写入时执行

[NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)
`hermes_cli/config_defaults.py`：

```python
"memory_char_limit": 2200,   # ~800 tokens at 2.75 chars/token
"user_char_limit": 1375,     # ~500 tokens at 2.75 chars/token
```

`tools/memory_tool.py` 按 target 选预算：

```python
def _char_limit(self, target: str) -> int:
    if target == "user":
        return self.user_char_limit
    return self.memory_char_limit
```

三条与本问题直接相关的设计判断：

1. **两份独立预算，互不侵占**。用户画像与仓库记忆各有上限，不存在
   「一侧吃光另一侧」——正是我们缺的。
2. **预算在写入时执行，超限直接拒绝**（`Adding this entry (N chars) would
   exceed the limit`），而非注入时静默丢弃。我们目前在 `renderFramed` 里
   `continue` 跳过：**丢了，但没有任何持久证据**（`dropped` 只进 debug 日志，
   而日志会轮转——与 [ADR 0006](0006-maintenance-failure-must-not-halt-the-pipeline.md)
   之前 `jobs.last_error` 那个教训同型）。
3. **单条 entry 也有上限**，并用作 drift 检测信号（`max_entry_len > char_limit`）。
   我们 personal 库那条 395 tok 的记忆能独占 30% 预算，就是因为缺这道约束。

### memorax-code —— 不可比，不据此下结论

[memorax-ai/memorax-code](https://github.com/memorax-ai/memorax-code) 与本项目
定位几乎相同（同样 Repo/Personal/Procedure 分类，同样支持 DSH），但全仓 grep
`budget|token_limit|char_limit` 在其 78 个 TS 与 8 个 Python 文件中**零命中**：
检索与预算逻辑在闭源的 MemoraX 服务端，本地只有 HTTP 适配层与采集层的
`commit_limit/pr_limit/issue_limit`（**条数**限制，与注入 token 预算无关）。
**故不作为本决策的依据。**

## 候选方案（评估记录）

1. **按来源切分预算**（personal 一份、repo 一份），每一侧的守卫对应一个真实容器。
   顺带修掉「一条 personal 记忆饿死整个 repo 派生层」。
   代价：改变注入语义，需同步规范 §4.2；两个子预算的数值需要有依据，不能拍板。
2. **只给 personal 侧设上限**，repo 侧用剩余。改动更小，但上限仍是一个要定的数，
   且 repo 可用额度仍随 personal 浮动。
3. **把「丢弃」从静默变成有据**：无论预算怎么分，`dropped` 都应落到可查状态而非
   debug 日志——否则下一次仍然要靠人工模拟才能发现。

无论选哪条，有两项独立于方案的缺口应一并考虑：**回退分支的 20×2000 无约束上限**，
以及**单条记忆缺注入侧上限**。

**最终选择方案 2**，但上限不是「一个要定的数」——这正是当初把它记为缺点的地方，
而该缺点可以消掉：上限取**最坏 L3 画像的渲染成本**，由同一条不变量算出（见下）。
于是它不是新增的第二个预算参数，而是**既有设计早已假定的那个数**被显式执行了一次。
方案 1 被否：切分预算要动 §4.2 的语义，而 §4.2 是规范不是调参旋钮；
且两个子预算是两个要维护的数，与「一条规则一个实现」相悖。

## 修复（2026-08-30）

### 更深一层的根因

此前本文把根因记为「共享容器」。那是对的，但**不够深**——共享容器只解释了
「为什么 personal 会挤占 repo」，没有解释「为什么 personal 的开销会失控」。
完整的因果链是：

```
D9 触发器在任何 personal raw 写入时删除 L3 画像
        ↓
queryInjectionRows 落到回退分支（无派生行 ⇒ 取最多 INJECT_TOP_N=20 条 L1 原子）
        ↓
该分支只限行数、不限体积（单行仅受 BODY_MAX_CHARS=2000 约束）
        ↓
personal 侧注入贡献无上界，实测 8 行 = 2348 tok > 整个预算 1300
        ↓
共享容器被 personal 吃光，repo 侧派生层 0/6 进包
```

关键在于**敞口是间歇性的**：画像在场时 personal 只花 ~168 tok，一切正常；
画像被删后才失控。实测 32.2 小时观测窗口内**画像存在 58.5%、缺失 41.5%**。
这解释了为什么此前的诊断反复摇摆——**同一个库在不同时刻给出不同的观测结果**，
而每一轮都只采了一个时刻的样。

### 两个独立的溢出源

必须区分，且**必须同一轮修完**：

| | 缺陷 A：personal 侧无上界 | 缺陷 B：写路径「请求 ≠ 约束」 |
|---|---|---|
| 位置 | `recall/inject.ts` 读路径 | `pipeline/rebuild.ts` 写路径 |
| 表现 | 画像缺失期 personal 吃光预算 | L2 块体系统性超发（最长 1820ch / 目标 900） |
| 触发 | 间歇（41.5% 时间） | 常驻（全部 17 个现存块无一例外） |
| 归属 | 与库无关，所有 repo 同时受害 | 所有库共享的写路径缺陷，此前只在一个库显形 |

只修 A 不够：`3e857510e628` 会从 6/6 **退到 5/6**（上界须按最坏画像计，
而非实测值），`edf7a686` 停在 3/6。只修 B 更不够：画像缺失期仍是 0/6。

### 统一的不变量

一条不等式，**同时给出两个数**：

```
worstPersona + ROLLUP_MAX_SCENARIOS × worstScenario ≤ INJECT_BODY_BUDGET_TOKENS
     171     +          6           ×      183      = 1269 ≤ 1300   富余 31
```

- `worstPersona` → **加载期守卫**中画像的份额，**同时**是运行时 personal 侧的上界；
- `worstScenario` → 反解出 `ROLLUP_TARGET_CHARS`，由写路径强制执行。

两处执行点共用 `constants.ts` 导出的 `worstPersonaTokens()` / `worstScenarioTokens()`，
**一条规则一个实现**：同一规则在两个不同容器上执行不算重复（`packetOverflows` 先例），
但同一个数字抄两遍算。

### 换行盲区（守卫的第二次自我修正）

`renderEntry` 会把 body 自带的 `\n` 缩进成 `\n␣␣`（每换行 +2 字符），而守卫原本用
单行合成 body（`'x'.repeat(n)`）定价，**看不见这个维度**：

```
密度  0    /千字 => 1247  OK
密度 11.94 /千字 => 1271  OK   ← 跨全部真实库的实测最大派生行密度
密度 33    /千字 => 1307  超预算，而守卫仍报绿灯
密度 80    /千字 => 1403  超预算
```

采纳方案 **(a)**：守卫按明确的最坏换行密度定价（`DERIVED_WORST_LINE_CHARS = 30`，
即每 30 字符一个换行）。该值由数据反推——跨全部真实库最密的一行是 **29.63/千字**，
30 向下取整到更短的行，使守卫定价略严于历史上出现过的任何数据。

**这不只是严谨性问题，它直接关系缺陷 A 的正确性**：真实库当前的 L3 画像含 4 个换行，
渲染成本 **168 tok**；若上界按单行定价取 161，**会把真实画像本身挤出注入包**——
用一个更严重的缺陷换掉缺陷 A。方案 (b)（只写注释）因此不可行：这里需要的不是
「记录边界」，而是让守卫和运行时上界都真正覆盖这个维度。

代价：`ROLLUP_TARGET_CHARS` 从 650 降到 **620**。650 是在单行定价下解出的，
按换行定价它落在 1317 > 1300。**常量跟随不变量走，而不是把不变量修剪成迁就常量。**
620 而非天花板 639：639 只余 1 tok，等于让守卫自身的假设成为承重结构；
620 余 31 tok，可承受**每换行字符数**低至 22 的块体，代价约 3% 的简报长度。

> **单位陷阱（这条把两轮审查各带偏一次，故写下来）**：`DERIVED_WORST_LINE_CHARS`
> 的单位是**每换行字符数**，不是**平均行长**——二者差一个 `+1`。一条 270 字符含
> 8 个换行的 body，平均行长是 30.0，但每换行字符数是 **33.75**。用「平均行长」
> 去反推安全边界，会高估约一行的余量。三个中间量应一并记住：
> **全体行最密 33.75 / 派生行最密 83.75 / 守卫取 30**。

**残余敞口（明确声明，不假装不存在）**：每换行字符数低于 **22** 的派生 body
（如逐词换行的 ASCII 列表）仍会超出定价。但**先落空的是 L3 画像，不是 L2 场景块**
——personal 上界先扣，且 `withinBudget` 对超限行整条跳过，故本 ADR 要保护的目标
（repo 侧派生层进包）在敞口下仍是 6/6，退化的是 personal 侧。该形态不是 rollup
提示词所要求的，且为它定价要牺牲真实简报长度。**「守卫绿灯」依然不等于「安全」**，
只是不安全区从「真实数据触手可及」推到了「本项目从未出现过的形态」。

### 顺带修正的观测口径

`dropped` 指标此前统计的是「拼接后被预算跳过的行数」。personal 上界会在拼接**之前**
就移除行，若不调整，这些行会从唯一能暴露该问题的信号里凭空消失——
**新上界会显得「免费」**。现改为对上界生效前的候选行计数（`inject.ts` 内有注释）。
这仍是 debug 日志（候选方案 3 未实施），但至少口径是诚实的。

### 未采纳

## 教训

1. **守卫必须建模运行时真正的容器，而不是它所属模块能看见的那部分。**
   `constants.ts` 只看得见常量，于是守卫只能断言常量之间的关系；而真实容器的占用
   由两个库的运行时内容决定。**模块的视野边界不等于问题的边界。**
2. **「asked for」与「enforced」是两个事实**（第 2 轮教训）。名字叫 target 的常量，
   可能只是提示词里的一句请求。动它之前先找到写路径真正的裁剪点。
3. **单库采样会产生 7 倍偏差。** 本项目把真实库列为第四权威源，但「一个库」不是
   「真实数据」——两次关键误判（换行密度、进包块数）都源于只看了一个库。
   建议把跨全部真实库的统计做成可重跑脚本纳入仓库。
4. **测试全绿 + 守卫绿灯，仍然可以零产品效果。** 这次是该教训的第二个实例
   （第一个是 L3 画像连续五天不可用而 153 测试全绿）。
   **判据只有一个：改动前后，真实数据上的行为差异。**

   修复时又撞到该教训的**第三个实例**，且这次是守卫自身：守卫用单行合成 body
   定价，对换行维度完全失明——密度 33/千字 即超预算而守卫照报绿灯。
   已按方案 (a) 修复（见「换行盲区」），但更该记住的是**发现方式**：
   它不是被守卫发现的，是被「守卫到底假设了什么形状」这个提问发现的。
   **守卫覆盖的维度，必须和它声称保护的量是同一组维度。**
5. **间歇性敞口会让单次采样自相矛盾。** 画像 58.5% 在场、41.5% 缺失，
   于是同一个库在不同时刻给出 5/6 与 0/6 两种观测，前三轮各采到一次，
   互相推翻。**采样不只要跨库，还要跨时间**——或者直接把产生差异的那个
   状态机（这里是 D9 触发器 + 6 小时维护周期）显式建模出来。
6. **修复必须成对时，任何一半单独上线都会退化。** 只修 A 会让某个库从
   6/6 退到 5/6（上界须按最坏画像而非实测值计）。
   「先修一半、观察一下」在这里是错的：判据要求的是**最坏情况下的行为**，
   而一半的修复恰好把最坏情况变成了常态。
