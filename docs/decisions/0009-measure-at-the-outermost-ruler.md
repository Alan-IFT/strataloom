# 0009 · 量到最外面那把尺子——`SOURCE_TURN_LIMIT` 是惰性常量

- 日期：2026-08-31
- 状态：已采纳（登记事实，暂不修实现）
- 相关：D3（证据可审计性）、D8（唯一渲染器）、`src/service.ts`、
  `src/store/conversations.ts`、`src/tools.ts`、`src/constants.ts`、
  [`0008`](0008-l0-records-what-tools-said-not-what-the-agent-did.md)

> 本文合并了一轮审计中三个议题的结论。**之所以合并为一份而非三份**：三者
> 共享同一个根因（量到了中间产物而非最终产物），拆开会让同一批数字在多处
> 复制——而那正是本仓库反复吃亏的地方。

## 一、事实：`SOURCE_TURN_LIMIT` 不绑定

`memory_recall(sourceOf:)` 的读路径上有**两把尺子，串联**：

```
service.source() → readSessionTurns(…, SOURCE_TURN_LIMIT = 34)      ← 行数
                 → tools.ts 把 turns 映射为 hits
                 → renderFramed(hits, RECALL_RESULT_BUDGET_TOKENS)  ← 500 token
```

第二把尺子先截断。全部 **11 个被引会话**实测（用编译产物的真实 `withinBudget`）：

```
LIMIT   20: 投递 mean=6.45  min=3  max=11
LIMIT   34: 投递 mean=6.82  min=3  max=12
LIMIT  100: 投递 mean=7.64  min=3  max=13
LIMIT 5000: 投递 mean=7.64  min=3  max=13     ← 与 100 完全相同
```

**投递量与 LIMIT 近乎无关**，且 100 以上完全封顶。原因可直接算出：

```
L0 单行渲染成本(tokens, withId=true): p50=41  p90=516  max=10457  mean=221.2
单行成本就 >500（永远投递不出去）的行: 394 / 3852 = 10.2%
实测 11/11 会话：预算在取满行数上限之前就截断
```

> 注意别只看 mean=221——分布极度右偏。真正让预算先截断的是 **p90=516 已超单条
> 预算**，以及 10.2% 的行单行就装不下。

**裁剪语义是 SKIP 而非前缀截断**：`withinBudget` 对超预算的条目 `continue`
（跳过后继续吸纳更便宜的行），故投递的行常常不是连续前缀。这一点影响修复
方案的可行性判断——见 §四。

## 二、它推翻了本仓库已交付的一次「修复」

[ADR 0008](0008-l0-records-what-tools-said-not-what-the-agent-did.md) 把该常量
由 20 提到 34，`constants.ts` 用 60 行注释论证这是「行预算面对行密度变化」的
**订正**，并给出重放实测（每会话 L0 行数 148.2→248.5、窗口字符 −34.3%、
assistant 行 −34.6%）。

**那些数字本身没错——它们准确描述了 `readSessionTurns` 返回集的性质。
错的是它们量的是 SQL 出口，不是用户出口。** 在用户出口上：

```
20 → 34 的差异: 投递 6.45 → 6.82 行
覆盖率:        完全不变
```

那次修复**没有改变任何一条证据的可见性**。

**准确的定性是「有成本、无收益」而非「纯空操作」**：调大 LIMIT 会增加 SQLite
扫描与 JSON 传输开销（LIMIT=5000 时原始成本达 32289 tok）却不改变输出——
这也是「不应把它调得更大」的独立理由。

> **危害在于它读起来极有说服力**：有推导、有重放、有盈亏平衡点。下一个人会
> 相信这条路径已经被量过了，从而不再去量。**附带完整论证形式的错误结论，
> 比空白更难纠正。**

## 三、连带：三次「覆盖率」测量全部停在同一个出口

为评估 `sourceOf` 是否失效，先后三次独立测量，方法各异，结果 **8.4% / 16.2% /
9.5%**——全部只算到「被引行是否落在 34 行窗口内」。把渲染预算接上重测：

```
落在 34 行窗口内            : 9.5%  (n=189，精确 seq 定位)
且挤进 500-token 预算(可见) : 2.1%
  窗口内命中被预算丢弃的比例: 77.8%
  被引行单行成本 >500 而永久不可见: 4/18
```

**三次测量方法不同、方向一致，却全部偏高 4–8 倍——因为它们共享同一个盲点。**
文档中此后只用**用户出口口径**：可见率 **2.1%**（精确定位样本 n=189）。

## 四、规范承诺的是「原话」，而兑现率是 2.1%

六处一致，无一处承诺「会话近况」：`plugin-architecture.md`「**当时到底怎么说的**」、
`conversations.ts` 模块注释「show the words behind it」、`readSessionTurns` 自己的
注释「the **"show me the original words"** path（核对原话）」、`tools.ts` 工具描述
「the original conversation **that memory came from**（checking exact wording）」、
`service.ts`「makes provenance **checkable rather than merely claimed**」。

而实现是 `ORDER BY seq DESC LIMIT n`——**取会话末尾**，与它上方那句注释直接
矛盾。证据均匀分布在整个会话中，被引行之后还压着 median≈216、p90≈954 行。

**但零使用实例。** 全部 151 个平台 session 日志（约 30.7 万行事件）：

```
memory_recall tool/call            : 1443
  其中 sourceOf 非空（排除空串/null/纯空白）: 61
  取值是 UUID（像 id 的）          : 0
  同一次调用还带着真实 query        : 61   ← 全部
  时间窗                            : 2026-08-24 一天
  在 059e0ce 修复之前                : 61   之后: 0
```

那 61 次**不是 sourceOf 的使用**：取值全是 `x`/`none`/`__omit__`/`null` 这类
占位符，每次都同时带着真实 `query`，无一个 UUID。它们正是 `059e0ce`
（「Treat "" as "omitted"」）那次修复的**病因样本**，修复后归零。

**结论：`sourceOf` 被有意使用的次数 = 0，成功返回过证据的次数 = 0。**

## 五、决策：登记，不修实现——但「不修实现」就必须改承诺

- **该修的理由**：规范六处承诺「核对原话」，兑现率 2.1%，是 D3 的核心承诺落空。
- **本轮不修的理由**：推荐方案（让 `evidence.excerpt` 复活为主证据源）覆盖率可
  达 100%、渲染成本从 avg 506 降到 p50 166，但它有三个前置必改项，构成一个
  完整议题：
  1. **`EXCERPT_COMPACT_MS = 30d` 必须重定。** 一旦 excerpt 成为主证据源，
     `decay.ts` 那条 compaction 就从「清理没人读的列」变成「**销毁 D3 的证据**」，
     而它比 L0（90 天）早死 60 天。不变量是「证据不得先于它所支撑的记忆或原话
     消失」；**更该先评估直接删除这条规则**——它节省约 80 KB。
  2. **`propose` 路径从不写 excerpt**（`service.ts` 的 INSERT 只有三列）。实测
     `principal-explicit` 证据行 **74/74 全 8 库**（其中 7 个 repo 库为 60/60）
     出生即 NULL。不补的话会出现最坏组合：**用户亲手保存的记忆，恰恰是唯一
     查不到出处的那一类。**
  3. **必须保留 L0 回退路径**，且回退时要在返回内容中**区分「这是引文」与
     「这是会话片段」**——混成同一批 hits 返回，审计者无法分辨看到的是证据
     还是上下文。
- **若最终决定不修实现，则必须修改承诺**：把 `tools.ts` 的工具描述与
  `plugin-architecture.md` 的条款改成它实际做到的事。**一个承诺核对原话却返回
  会话末尾数行的工具，是在文档层面撒谎——两者不可都留。**

## 六、已被实测否决的方向（连同算术留档，以免重提）

- **(a) 调大 `SOURCE_TURN_LIMIT`** —— 不是「代价太大」，是**完全无效**：
  20→5000 投递量 6.45→7.64 后封顶，覆盖率不变。此前一度以为它的代价是
  「撑爆预算」——实际**连撑爆都做不到**，`withinBudget` 会静默丢弃多取的行。
- **(b) 改取会话开头 / 文本定位** —— 换锚点同样错（证据均匀分布）；文本定位
  技术可行（按 `\n---\n` 拆段 + label 精确相等 + 前缀匹配，定位成功率
  **357/358 = 99.7%**），但需要先有 excerpt，而一旦有了 excerpt，直接渲染它
  已拿到答案，再去 L0 换回同一段是多绕一圈；且对 74 条 `principal-explicit` 无解。
- **(c) 把 `sourceSeqs` 持久化进 `ref`** —— **实测有害**。`ref` 有 **4 个消费者**，
  3 个按**等值**匹配：`conversations.ts` 的 prune 保护、`service.ts` 的 sourceOf、
  **`extract.ts` 的 tombstone 来源抑制**、以及 `schema.ts` 的主键与索引。
  只读副本实测：改成 `session-<uuid>#<seq>` 后，本应受保护的 L0 行
  **2439 → 0**，且来源抑制同时失配（被 forget 的记忆会被重新学回来，违反 D5）。
  这不是「零新增机制」，是**在一个被四方共享的键上偷改编码**——D7–D9 同型。

  > 附带更正：`sourceSeqs` **不是**「算完 provenance 就丢弃」——它紧接着被用来
  > 构造 `excerpt` 并落库。它的信息以**文本形式**持久化了，只是没有以 **seq
  > 形式**持久化。把它说成「白拿的信息源」会低估修复成本。

## 七、顺带登记（不在本轮处理）

- **`evidence.excerpt` 与 `superseded_by` 都是只写不读的死列**：前者仅
  INSERT + 两处 `UPDATE = NULL`，后者仅两个写点，生产代码零 SELECT。
  「本仓库存在一类只写不读的列」由孤例变成了模式。
- **90 天 L0 保留期尚未触发**：`pruneConversations` 的豁免子句使保护集恒等于
  全集（3852/3852 行，逐库 N/N），故时间条件至今无关。**但它不是死代码**
  ——上面 (c) 的实测（2439→0）恰好证明**它此刻正在承载保护语义**。正确措辞是
  **「尚未触发」而非「从未生效」**：首次可能触发在 **2026-11-21**。
  体积：文本字节率 **576.7 KB/天**，L0 落盘放大 **1.30×**，L0 占库页 **71.7%**，
  90 天稳态约 **65.8 MB**，小于 `~/.dsh/sessions` 今天的 79.4 MB。
  零损害实例，本轮不动。
- **`RECALL_RESULT_BUDGET_TOKENS = 500` 同时服务三类体量不同的内容**：
  `memory_recall` 结果与 `propose` 近重复列表的条目受 `BODY_MAX_CHARS` 约束，
  而 `sourceOf` 喂进去的是**无长度上界的 L0 原文**（单行 p90=809）。这是 ADR
  0007「一个容器被不同来源争抢」的形状。**但渲染器必须继续共用（D8）**——
  可疑的是共用同一个数值，不是共用同一个函数。
- **`scripts/inspect.mjs` 的 `--days abc` → `NaN`**，导致 `created_at >= NaN`
  恒假、静默返回空结果，不报错。

## 八、教训

1. **一条读路径上有几把尺子，就要量到最外面那一把。** 三次独立测量、三种
   方法，全部停在 SQL 出口，全部偏高 4–8 倍。中间产物不是最终产物。
2. **附带完整论证形式的错误结论，比空白更难纠正。** `constants.ts` 那 60 行
   推导有数据、有重放、有平衡点，唯独没有走到用户出口。
3. **「不修实现」与「不改承诺」不可兼得。**
4. **调研工具本身会静默丢数据。** 平台 session 日志是**多帧 zstd**，而
   `node:zlib` 的 `zstdDecompressSync` **只解第一帧**——151 个文件每个只读到
   头部一行，一度得出「0 次调用」的错误结论，直到与已知的 41 次矛盾才暴露。
   它不报错、不抛异常，只是少给 99% 的数据。**走 session 日志的调研必须用
   `zstd -dc`。**
5. **单样本会在最后一刻再骗你一次。** 本文初稿写「投递恒为 4 行」——那是
   单个会话的读数；全量 11 会话是 6.45→7.64。结论（常量不绑定）不变，
   但「恒定」与「近乎无关」是两个强度不同的断言，而证据只支持后者。
