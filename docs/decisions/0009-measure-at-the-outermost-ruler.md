> **本文的数字口径约定**（初稿因缺少这一节而出错六处）：
> - 凡绝对数一律标注**测量时刻**——库在持续增长，本文写作期间 L0 就从 3852
>   涨到 4075 行；

> - 凡单会话/单库读数**显式标注**，不与全样本混用。
>
> 合并为一份而非三份：三个议题共享同一根因（量到中间产物而非最终产物），
> 拆开会让同一批数字在多处复制——那正是本仓库反复付出代价的地方。

## 一、事实：`SOURCE_TURN_LIMIT` 不绑定

`memory_recall(sourceOf:)` 的读路径上有**两把尺子，串联**：

```
service.source() → readSessionTurns(…, SOURCE_TURN_LIMIT = 34)      ← 行数
                 → tools.ts 把 turns 映射为 hits
                 → renderFramed(hits, RECALL_RESULT_BUDGET_TOKENS)  ← 500 token
```

`tools.ts` 的那个 `renderFramed` 是 `memory_recall` 的**唯一** render 回调，
两种模式（query / sourceOf）共用——这是 D8 的明文要求，不是巧合。

**第二把尺子先截断。** 快照 `L0 = 3852 行`（`created_at < 2026-08-30T14:41:34.722Z`），
11 个被引会话，用编译产物的真实 `withinBudget`：

```
LIMIT   20: 投递 mean=6.45  min=3  max=11
LIMIT   34: 投递 mean=6.82  min=3  max=12
LIMIT  100: 投递 mean=7.64  min=3  max=13
LIMIT 5000: 投递 mean=7.64  min=3  max=13     ← 与 100 完全相同
```

> **样本口径**：`evidence` 中 `kind='session'` 且记忆非 tombstone 的 distinct
> `ref` 实为 **12 个**；「11 个」是其中**实际存有 L0 行**的那些。
> `session-c53b1a7b` 只被 `global.sqlite` 的记忆引用，而 global 的
> `conversations` 表为空，投递恒为 0，计入会污染均值。

原因可直接算出（同一快照，`withId=true`，与工具实际渲染口径一致）：

```
L0 单行渲染成本(tokens): p50=41  p90=516  max=10457  mean=221.2
单行成本 >500（永远投递不出去）的行: 394 / 3852 = 10.2%
11/11 会话：预算在取满行数上限之前就截断
```

> 不要只看 mean=221——分布极度右偏。**更稳的支撑是后两项**：约 10% 的行单行
> 就装不下，以及 11/11 会话预算先截断。（p90 会随数据漂移：复核时已从 516
> 降到 502，仍 >500，但把结论挂在一个 0.4% 余量的不等式上是脆弱的。）

**裁剪语义是 SKIP 而非前缀截断**：`withinBudget` 对超预算条目 `continue`，
跳过后继续吸纳更便宜的行。实测 **9/11 会话**投递行不是连续前缀，空洞中位数 5、
最大 14。**用户看到的是窗口内被成本筛过的散点**，既不是原话的连续片段，
也不是「最近 N 行」。

## 二、它注销了本仓库一次已交付修复的收益

[ADR 0008](0008-l0-records-what-tools-said-not-what-the-agent-did.md) 把该常量
由 20 提到 34，`constants.ts` 用约 60 行注释论证这是「行预算面对行密度变化」
的**订正**，并给出重放实测（每会话 L0 行数 148.2→248.5、窗口字符 −34.3%、
assistant 行 −34.6%）。

**那次推理在它所选的层面上是有效的。** 复核在当前库上直接验证：20→34 使
窗口字符 **+93.5%**、assistant 行 **+50.8%**——在 SQL 出口，提高 LIMIT 确实
买到了大幅更多的内容。

**但那个层面不是最终产物。** 在用户出口：

```
20 → 34: 投递 6.45 → 6.82 行；11 个会话中 8 个投递集合逐条完全相同
覆盖率: 四档 LIMIT 上恒为同一个值，一条不多（逐条追踪，非均值巧合）
```

**准确的说法是「注销了那次修复的收益」，不是「推翻了它」**——缺陷在**作用域**
（量到中间产物），不在逻辑。

**而且它有成本。** 全样本（11 会话，LIMIT=5000，2026-08-31 测）：

```
原始取回成本: 合计 901654 tok  均值 81969  最坏单会话 240670
20→34 使每次调用的原始取回 +91%，而投递恒定在 ~450–500 tok
无效取回率: 88.7% → 94.0%
```

**「有成本、无收益」，而非纯空操作。**

> **危害在于它读起来极有说服力**：有推导、有重放、有盈亏平衡点。下一个人会
> 相信这条路径已经被量过了，从而不再去量。**附带完整论证形式的错误结论，
> 比空白更难纠正。**

## 三、连带：三次「覆盖率」测量全部停在同一个出口

为评估 `sourceOf` 是否失效，先后三次独立测量，方法各异，结果
**8.4% / 16.2% / 9.5%**——全部只算到「被引行是否落在 34 行窗口内」。

**其中 8.4% 与 16.2% 经穷举反解（多种分子×分母×LIMIT×库子集）无法复现，
应当作废。** 它们大概率来自 `instr` 子串匹配——实测该方法比构造式反演
**放大 2.97×**（同一数据上 404 段被匹配成 1198 对）。

把渲染预算接上，用**构造式反演**定位（按 `extract.ts` 的写入规则反向重放，
往返逐字节校验 **209/209 通过、0 失败**）：

```
口径：evidence(kind='session') 行，排除 tombstone，n=282（2026-08-31）
      含 75 条 excerpt 为 NULL 的行——它们在用户出口上同样不可见，故计入分母
落在 34 行窗口内            : 7.4% – 10.6%
且挤进 500-token 预算(可见) : 2.1% – 4.3%     ← 区间来自 34 个多解段
  窗口内命中被预算丢弃的比例: 60.0%
若改用「可精确定位样本」为分母(n=181): 落窗 10.5%，可见 3.3%
```

**区间不应压成点估计**——宽度来自真正不可判定的多解段（同一段文本在会话中
被反复输出，最极端一条有 900+ 个候选 seq）。

> **本文初稿在这里犯了自己正在批评的错误。** 它写「2.1%（精确定位样本
> n=189）」：`n=189` 在任何自然口径下都不存在（实际是 284/282/209/181），
> 而 2.1% 唯一能复现的方式是 `6/284`——**分子只数能精确定位的（子集），
> 分母是全部证据行（全集）**。按它自己贴的标签应是 `6/181 = 3.3%`。
> **在纠正一个口径错误的过程中引入了另一个口径错误。**

## 四、规范承诺的是「原话」，实现取的是会话末尾

全仓 **11 处**承诺「原话 / original words / exact wording」，无一处承诺
「会话近况」。其中三处尤其重要，因为它们是**运行时真正喂给模型的文本**：
`tools.ts` 的 `sourceOf` 参数描述、`tools.ts` 注入给每个 agent 的 GUIDANCE、
以及 `docs/design/4x4-memory.md` 把该能力现状标为「✅ 完整」。

而实现是 `ORDER BY seq DESC LIMIT n`——**取会话最末 34 行且逆序**，全路径
无 `reverse`。它与其**正上方两行**的注释直接矛盾（注释说「show me the
original words / 核对原话」），且该 SQL 自初始提交起从未变过。

**但零使用实例。** 全部平台 session 日志（157 文件 / 309336 行事件，
`zstd -dc` 解压）：

```
memory_recall tool/call            : 1443
  其中 sourceOf 非空（排除空串/null/纯空白）: 61
  取值是 UUID / 与真实 memories.id 有交集   : 0 / 0
  同一次调用还带着真实 query        : 61 / 61   ← 全部
  时间窗                            : 2026-08-24 的 84 分钟内，7 个 session
  在 059e0ce 修复之前 / 之后         : 61 / 0
  这 61 次的结果                     : 61/61 全部 isError，
                                       "Error: no memory with id <值>"
```

取值全是 `x`(21) / `none`(16) / `__omit__`(6) / `null`(3) 这类占位符，其中
`nonexistent-check-do-not-use` 与 `mem_0000…0` 是模型的**自述意图**。它们正是
`059e0ce`（「Treat "" as "omitted"」）的病因样本。修复后 202 次真实调用中
`sourceOf` 非空为 0，而该键仍被发送 197 次（值为 `""`）——**因果链闭合，
不是「后段无样本」造成的假象**。

**结论：有意使用 0 次，成功返回证据 0 次（后者为实测，非推论）。**

> **但这个「0」有边界。** 采样窗口只有 8 天，且几乎全是开发者在调试本插件，
> 而非正常使用记忆系统——真正会想「核对原话」的场景（跨周回看某条记忆的
> 来源）在窗口内几乎没有机会发生。**更准确的表述是「现有观测窗口内从未被
> 有意使用」，而非「该能力无需求」。**
>
> 还有一个结构性因素：`(id …)` 只在 `memory_recall` 的搜索结果里出现，
> **注入路径不带 id**。模型必须先做一次搜索、且结果没被预算截断，手里才会有
> 可回传的 id。「零使用」里有多少是「不需要」、多少是「拿不到 id」，
> 现有数据无法区分——**这对第五节的决策有直接影响。**

## 五、决策：登记，不修实现——但「不修实现」就必须改承诺

- **该修的理由**：11 处承诺「核对原话」，兑现率 2.1%–4.3%，是 D3 的核心承诺落空。
- **本轮不修的理由**：推荐方案（让 `evidence.excerpt` 复活为主证据源）有三个
  前置必改项，构成一个完整议题：
  1. **`EXCERPT_COMPACT_MS = 30d` 必须重定。** 一旦 excerpt 成为主证据源，
     `decay.ts` 那条 compaction 就从「清理没人读的列」变成「**销毁 D3 的证据**」，
     而它比 L0（90 天）早死 60 天。不变量是「证据不得先于它所支撑的记忆或原话
     消失」；**更该先评估直接删除这条规则**。
  2. **`propose` 路径从不写 excerpt**（`service.ts` 的 INSERT 只有三列）。
     实测 `principal-explicit` 证据行 **74/74（全 8 库）** 出生即 NULL，
     其中 7 个 repo 库为 60/60（样本集中在 4 个库；另 3 个该类证据为 0）。
     **反证组是决定性的**：同期 `tool-output` 仅 1/184 为 NULL、`parent-agent`
     0/23——排除了「被 compaction 清空」的替代解释。
     不补的话会出现最坏组合：**用户亲手保存的记忆，恰恰是唯一查不到出处的那一类。**
  3. **必须保留 L0 回退路径**，且回退时要**区分「这是引文」与「这是会话片段」**
     ——混成同一批 hits 返回，审计者无法分辨看到的是证据还是上下文。
- **若最终决定不修实现，则必须修改承诺**：改 `tools.ts` 的工具描述与 GUIDANCE、
  `plugin-architecture.md` 的条款、以及 `4x4-memory.md` 里那个「✅ 完整」。
  **一个承诺核对原话却返回会话末尾数行的工具，是在文档层面撒谎——两者不可都留。**

## 六、已被实测否决的方向（连同算术留档，以免重提）

- **(a) 调大 `SOURCE_TURN_LIMIT`** —— **收益极小且不可预期**：11 会话中 6 个
  渲染全文逐字相同、5 个只增不减；唯一显著变化的 `4e634938` 开头压着一条
  35k+ 字符的巨行，放宽后可见内容 5→10 行。而成本确定（见 §二）。
- **(b) 改取会话开头 / 文本定位** —— 换锚点同样错（证据均匀分布）；文本定位
  技术可行，但需要先有 excerpt，而一旦有了 excerpt，直接渲染它已拿到答案；
  且对 74 条 `principal-explicit` 无解。
- **(c) 把 `sourceSeqs` 编码进 `ref`** —— **实测有害，三个读者同时静默失配**
  （2026-08-31 全库口径）：

  ```
  prune 保护行数        : 4013 → 0     （全库；撰写时 3852）
  sourceOf 可解析的记忆 :  269 → 0
  来源抑制命中          :    2 → 0
  ```

  且**端到端复现了 D5 违反**：用真实 `runExtractJob` 跑通，被 `memory_forget`
  过的内容在改编码后**被重新学回**（抑制查询失配时函数直接 `return`，
  后果不是「少一条保护」而是**整批放行**）。

  > **最有力的证据不是数字，是它测不出来。** 在包副本上打了该补丁跑完整套
  > 171 个测试：**只有 1 个断言字面量的测试失败，3 个语义守护测试全部通过**
  > ——因为它们手写 `INSERT INTO evidence … VALUES (…,'sess-1')` 造证据行，
  > **绕过了真实写者**，于是读写两侧在测试里始终自洽。
  >
  > **定性更正**：这不是 D7–D9 的「一条规则两处实现而漂移」（本案只有一个
  > 写者、没有第二份实现）。它的形状是**「一个键的编码契约被多个读者隐式
  > 共享，写者单方面变更」**。这比 D7–D9 更难防：双实现漂移至少能靠比对
  > 两份代码抓到。
  >
  > 另一个未记的后果：PK `(memory_id, kind, ref)` 将不再按会话去重，
  > `forget()` 回给用户的 `suppressedRefs` 计数会虚高（实测 1→3）。

  > **附带更正**：`sourceSeqs` **不是**「算完 provenance 就丢弃」——它紧接着
  > 被用来构造 `excerpt` 并落库。信息以**文本形式**持久化了，只是没有以
  > **seq 形式**持久化。真正缺的不是信息，是**一个能承载 seq 的位置**。

## 七、顺带登记（不在本轮处理）

- **三个「值从不被生产读路径消费」的列**，构成一个模式而非孤例：
  `evidence.excerpt`（无任何消费者）、`memories.superseded_by`（值不被读，
  但作为外键仍在承载引用完整性约束）、`jobs.last_error`（生产代码零 SELECT，
  但 `scripts/inspect.mjs` 会读并打印）。
  **三者共享同一生成机制**：写入方按「将来会有人读」落库，读取方从未落地，
  而**类型系统与测试都无法报警**——测试反而通过断言写入正确，给了它们
  「已被覆盖」的假象。
  **措辞须限定为「值从不被生产读路径消费」**，否则会误导出「可以 DROP COLUMN」
  的结论。
- **90 天 L0 保留期尚未触发**：`pruneConversations` 的豁免子句使保护集恒等于
  全集（2026-08-31 实测 4075/4075，7 个非空库逐库 N/N；global 为 0 行，
  其 N/N 是空真、不提供证据）。**但它不是死代码**——反事实检验：
  有该子句时删 0 行，去掉它则删全部 4075 行。正确措辞是**「尚未触发」而非
  「从未生效」**。
  时间条件首次可能满足于 **2026-11-21**（首次提交 + 90 天，与最早 L0 行推算
  同日）；**但届时预计实际删除量仍为 0**，因为那批行 100% 被豁免。
  体积（2026-08-31）：文本**字节**率 576.7 KB/天（分母为 max−min 跨度 6.97 天，
  含 3 个零活动日，属保守取法）；90 天稳态 **L0 页约 66–69 MB，整库约 92 MB**。
  零损害实例，本轮不动。

  > **两处口径更正**（初稿错，且都是本文批评的同型错误）：
  > ① 初稿写「90 天稳态落盘 65.8 MB」——那是 **L0 页**，而「落盘」一词暗示
  > 整库；补回非 L0 的 28.3% 后是 **~92 MB**。**在批评「量到内层尺子」的
  > 文档里，自己把尺子从整库缩回了 L0 页。**
  > ② 初稿拿它与 `~/.dsh/sessions` 的 79.4 MB 比较——**那是 zstd 压缩后的
  > 字节（解压约 196.7 MiB），且是 9 天累积而非 90 天稳态**。同口径应是
  > ~92 MB vs ~785 MB。结论（体积无害）不变且更强，**但理由必须换**——
  > 错误的理由会在下一次数据变化时失效。
  >
  > 更早一版还写过 431.8 KB/天与 2.38× 放大。复核发现这两个错误在乘法中
  > **互相抵消**（字符数同时出现在分子分母），其乘积 ~90 MB 反而接近整库真值。
  > **两个错误口径产生一个正确答案，比单纯算错更危险——最终数验算通过会
  > 掩盖中间量不可用。**
- **`RECALL_RESULT_BUDGET_TOKENS = 500` 同时服务三类体量不同的内容**：
  `memory_recall` 结果与 `propose` 近重复列表的条目受 `BODY_MAX_CHARS` 约束，
  而 `sourceOf` 喂进去的是**无长度上界的 L0 原文**。这是 ADR 0007「一个容器被
  不同来源争抢」的形状。**但渲染器必须继续共用（D8）**——可疑的是共用同一个
  数值，不是共用同一个函数。
- **`scripts/inspect.mjs` 的 `--days abc` → `NaN`**，使 `created_at >= NaN`
  恒假、静默返回空结果，不报错。

## 八、教训

1. **一条读路径上有几把尺子，就要量到最外面那一把。** 三次独立测量、三种
   方法，全部停在 SQL 出口。中间产物不是最终产物。
2. **附带完整论证形式的错误结论，比空白更难纠正。** `constants.ts` 那 60 行
   推导有数据、有重放、有平衡点，唯独没有走到用户出口。
3. **「不修实现」与「不改承诺」不可兼得。**
4. **调研工具本身会静默丢数据。** 平台 session 日志是**多帧 zstd**（实测单文件
   含 6270 帧），而 `node:zlib` 的 `zstdDecompressSync` **只解第一帧**——
   157/157 个文件每个只得 1 行，合计 157 行 vs `zstd -dc` 的 308995 行，
   **不报错、不抛异常，静默少给 99.95% 的数据**。走 session 日志的调研必须用
   `zstd -dc`。
5. **单样本会在最后一刻再骗你一次。** 本文初稿有三处把子集当全集：
   「投递恒为 4 行」（单会话；全量 6.45→7.64）、「LIMIT=5000 原始成本 32289 tok」
   （单会话中位数；全样本合计 901654、最坏 240670）、「受保护 2439 行」
   （单库快照；全库 4013，且已增至 4075）。**绝对数必须标注是哪个集合、
   哪个时刻。**
6. **纠正一个口径错误时，最容易犯下另一个口径错误。** 本文初稿在批评
   「只量到 SQL 出口」的同一节里，把「精确定位样本」的分子除在了「含 26%
   无法定位样本」的全集分母上；在批评「量到内层尺子」的同一节里，把体积的
   尺子从整库缩回了 L0 页。**分子分母必须同时量到那把尺子。**
7. **破坏能不能被测试抓到，和破坏有多严重无关。** §六(c) 的改动会让三个读者
   静默失配并违反 D5，但 171 个测试里只有 1 个会红——因为语义测试自己扮演
   写者、用旧编码造数据。**当测试绕过真实写者时，它验证的是自己的假设，
   不是产品的契约。**
