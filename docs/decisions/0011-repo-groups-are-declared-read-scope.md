## 一、问题：一个工作树，四个互不相通的库

`/home/alan/Programs/NFBY_CMS_FullStack` 是控制平面仓，其工作树内**并列检出三个独立
git 仓**（被父仓 `.gitignore` 忽略，非 submodule）：

```
FullStack/            remote:github.com/Alan-IFT/NFBY_CMS_FullStack   94394b03…  66 条
├── NFBY_CMS_Backend/ remote:github.com/Alan-IFT/NFBY_CMS_Backend     edf7a686…  16 条
├── NFBY_CMS_Frontend/remote:github.com/Alan-IFT/NFBY_CMS_Frontend    ec2636fc…  16 条
└── NFBY_CMS/         remote:github.com/Alan-IFT/NFBY_CMS             12be5e2a…  （无库）
```

用户在 FullStack 根开会话、让 AI 同时改前后端；实测 3 个 FullStack 会话全部同时改动了
两个子仓。而 `deriveRepoIdentity` 按 git remote 派生键，于是子仓记忆对 FullStack 会话
**完全不可见**。

此外仓库改名（`NFBY_CMS_Ops` → `NFBY_CMS_FullStack`）静默分裂出一个孤儿库
`3e857510…`（33 行：27 条 L1 + 6 个 L2 块），**该仓在本机已无任何 checkout**。

> **顺带纠正一个易错点**：`NFBY_CMS` 派生键是 `12be5e2a…`，而 `repos/` 下**没有**这个
> 目录。它满足准入条件 (a)（确实是工作树内的 checkout），但会在「成员库不存在」这一步
> 被跳过并 warn。**「合法成员」与「有库可读」是两件事**，代码分两步判定。

## 二、把设计钉死的实测事实

这几条不是偏好，是测出来的约束；任何后续修改必须先推翻它们。
§2.1–2.3 定于第一、二轮，§2.4–2.5 由第三轮 QA 在**真实数据 + 真实调用链**上
证伪后补入——它们抓到的正是前四轮纯看代码看不见的问题。

### 2.1 注入路径绝不跨库合并

三库合并注入 = **4104 tok**（四库 5183 tok），对 `INJECT_BODY_BUDGET_TOKENS = 1300`
是 **3.16×／3.99×**。而 ADR 0007 的不变量 `171 + 6×183 = 1269 ≤ 1300` **只剩 31 tok
富余**，最便宜的外仓 L2 块是 166 tok。**一块都塞不进去。**

⇒ `recall/inject.ts` **一行未改**。组内容永不进入注入包。

### 2.2 跨库 BM25 `rank` 不可比

FTS5 的 `rank` 是负 BM25，其 IDF 由**各库自己的 N 与 df** 算出。于是一个词在某库越是
**主题词**（df/N 越高），IDF 越低，rank 越**差**。实测反转率 **85.2%**（311 个查询中
265 个），另一路独立复核 6/6 全反转。典型例：

```
查询「部署」  rank 冠军：Frontend（1 条附带命中）
              rank 垫底：Ops（真正管部署，14 条命中，df/N = 42.4%）
```

⇒ 排序**位置式**：本仓优先 → 外仓按 members 书写序。**全局 `ORDER BY rank` 会精确地
编码相关性的反面。** 测试 11 锁住这一点，且**故意不断言**外仓之间的 rank 顺序——
断言它等于把「不可比」当「可比」锁进回归测试。

### 2.3 recall 需要**两级容器**：每库预算 + 与之匹配的最外层预算

**本节在第二轮被推翻并重写——原论证的因果不成立。**

原文写的是：「共用单一 500 tok 容器时 33.1%~40.9% 的查询本仓被挤掉；改每库预算后
本仓进包逐条相等」。**后半句为真，但它不是前半句的功劳。** `recall()` 恒先 push 本仓、
`withinBudget` 按优先序扫描并**跳过**超限项 ⇒ 本仓交付**与外仓行数无关**，
只取决于「本仓先入」这一顺序。实测：外仓无界（每库 200 行）与有界（200 tok）两种配置下，
本仓 title 列表**完全相同**。所以那个观察锁的是**顺序**（已由用例 11 覆盖），
对「每库预算是否必要」**零信息量**——用它论证每库预算的必要性同样站不住。

每库预算真正的作用是**给外仓设上界**，从而让最外层容器在加载期**可定价**；
它与「本仓零回归」没有因果关系。删掉它，本仓零回归**依然成立**。
用例 5 已改为直接证伪这一点：外仓 6 行与 **200 行**时本仓交付逐条相等。

而**只有每库预算是不够的**——这是第二轮发现的真缺陷。`tools.ts` 曾用
`renderFramed(hits, RECALL_RESULT_BUDGET_TOKENS /* 500 */)` 渲染**全部** hits，
即本仓与外仓同吃一个 500 的**共享**容器。因为本仓恒先入，它一行不丢，
**所有零回归断言全绿**，而外仓被挤成空。实测（真实 4 库，1936 机械种子，
在 `renderFramed` 出口计数）：

| 本仓结果 token | 种子数 | 获得外仓行的种子 | 比率 |
|---|---|---|---|
| 0 | 1010 | 983 | 97.3% |
| 1–249 | 386 | 189 | 49.0% |
| 250–499 | 154 | 38 | **24.7%** |
| 500–999 | 170 | 39 | **22.9%** |
| ≥1000 | 216 | 14 | **6.5%** |

即**本仓越充实，外仓越读不到**：功能开着、人审批过了、结果恒空。
这是 ADR 0007 教训 4（守卫绿灯 + 零产品效果）与 ADR 0009（在最外层尺子上量）的合体。

⇒ 定稿为**两级容器，各自独立**：service 层给本仓一个
`RECALL_RESULT_BUDGET_TOKENS`、给每个成员一个 `RECALL_FOREIGN_BUDGET_TOKENS`；
渲染出口用 `RECALL_PACKET_BUDGET_TOKENS` = **两者之和**，于是渲染**永不裁掉
service 已准入的行**，它只负责加框。同一回放订正后：外仓获益种子
65.2% → **78.6%**，≥1000 档 6.5% → **75.5%**，本仓交付
**1936/1936 与关组基线逐条相等**。

> **本仓裁剪必须下沉到 service 层**，这是订正的必要配套：最外层预算把本仓额度
> 写进了守卫的前提，本仓就必须真的受该额度约束。否则本仓行数一多便吃满整包，
> 外仓交付重新归零——缺陷只是**外移了一层**。实测未下沉时本仓 20 行即把外仓压回 0。

**被数据否决的替代方案**：从 500 里**划出**固定份额给外仓（本仓 300 + 外仓 200）。
实测它**破坏硬闸 7**——本仓交付在 **521/1936** 个种子上偏离关组基线，**丢失 612 行**。
「给客人留位靠向主人收税」正是本设计要禁止的驱逐，故方向作废。

### 2.4 外仓**一个字节都不写**——第三轮 QA 端到端证伪后定案

前两轮 `recall()` 对每个成员库调 `touchUsage(member.store, admitted)`，
辩护词是「`usage` 非权威，D4 允许读路径写它」。**两半都错，且是实测证伪的。**

**（a）跨仓之后它就不是非权威的。** `pipeline/decay.ts` 的模块注释自己写着
「revival happens **HERE, never on the read path**, because a read must not cause
an authoritative change (D4)」，而它 `SELECT … FROM usage WHERE last_hit_at >= ?`
去写 `memories.status`。链条在**同仓内**是闭合的（读的人就是库的主人），
**跨仓就不是**。在真实库副本上做对照实验（Backend 补到 61 条陈旧 active 行以越过
`DECAY_MIN_ACTIVE=50` 地板）：

```
【对照组】外仓自跑 decay，本会话不检索:      active 61 -> 0    (slept 61)
【实验组】FullStack 会话先 7 次纯读再 decay:  active 61 -> 4    (slept 57)
>>> 因本会话「只读」而免于休眠的外仓记忆 = 4 条
>>> 幸存者中被本会话读过的: 4/4     ← 因果确凿
```

**一次纯读检索，改写了另一个仓库的权威状态。**

**（b）「不 touch 就会被 decay 掉」的担忧两个分支都不成立。**
成员库**自己有会话** ⇒ 它自己的读就会 touch，本循环多余；
成员库**没有会话**（改名分裂出的孤儿库 `…_Ops`，本机无 checkout）
⇒ **让它按自己的节奏衰减本就是正确行为**。用另一个仓的活动无限期给一个
已废弃的库续命是错的。实测那些写入**确实打到了孤儿库**。

**（c）它让审批提示成了不实陈述。** 提示语「Nothing is ever written to them」
是 archived 成员唯一的承重闸（§3.2），而实测 7 次 recall 改了 Backend 库 4 行 usage、
孤儿库 4 行，**两个库的 md5 与 mtime 全变**。人是照着这句话点的同意。

⇒ **删掉外仓 `touchUsage`。** 一处修复同时关掉两个问题：D4 不再被穿透，
提示语自动变成真话。`service.ts` 的 `touchUsage` 文档收紧为
「**只能对 `readableStores()` 的库调用**」，并写明理由。
审批提示同时**变得更具体**：明说「no memory there is saved, changed, forgotten,
or even **marked as used**」——因为「标记为已使用」正是那个被辩护了很久的写。

用例 17 用**文件 md5 + usage 快照**锁住（不是断言「没调某函数」，
而是按人会怎么验去验）；用例 17b 用**对照/实验双臂**锁住 D4 不被穿透。
变异测试：把 `touchUsage(member.store, admitted)` 放回去，**17 与 17b 同时变红**。

### 2.5 recall 结果必须**逐条可归因**（第三轮阻断 3）

`FRAMING_HEADER` 固定写「…from previous sessions **in this repository**」，
而 `MemoryHit` 无来源字段、output schema `additionalProperties:false`——
**连放的地方都没有**。QA 实测 2792 个查询中 **1508 个（54.0%）** 返回内容
**100% 来自外仓**，却挂着「本仓」抬头：查「部署」返回的
`exec 式部署入口 outer(N)+inner(N+1)` 来自**已改名分裂、本机无 checkout 的 Ops**，
`VITE_API_URL 必须重建` 来自 **Frontend**。模型与用户都会当成本仓事实用。

**这是内部不一致，不是设计争议**：`/memory` list **已经做对了**
（`MemoryListingScope` 专门扩宽以携带 `source`，其注释原话是
「完整但不可归因不算完整」）。同一意图在 list 落实、在 recall 遗漏。

⇒ 两处最小改动：
- `RenderableHit` 增加**可选** `source`，`renderEntry` 有则渲染 `(from …) `。
  **缺省即「本仓/personal」**——所以注入包、`propose` 近重复表、`sourceOf` 转录
  **一个字节不变**（用例 18b 逐字节断言）。
- 抬头**二选一**：含外仓条目用 `FRAMING_HEADER_MIXED`，否则用原常量**原样**。
  不改写单一常量，正是为了保住上面那条逐字节闸。

标注**在预算之前**贴（用例 18c 锁死）：贴在 `withinBudget` 之后，
每条会比预算被告知的大出约 9 tok，正是 D8「定价的串 ≠ 渲染的串」。
`SOURCE_LABEL_MAX_CHARS = 64` 是**必需的上界**而非美观（声明文件是手写的、长度无界，
否则加载期根本无法给最坏行定价）；真实 source 实测 37–45 字符，全部完整显示。

## 三、准入判据（修法 3）

声明文件 `<workspace>/.strataloom-group.json`，member 支持字符串简写
（等价于 `{source, archived:false}`）：

```json
{ "version": 1, "group": "nfby-cms",
  "members": ["remote:github.com/Alan-IFT/NFBY_CMS_Backend",
              { "source": "remote:github.com/Alan-IFT/NFBY_CMS_Ops", "archived": true }] }
```

- **(a) 工作树内成员**（`archived` falsy）：须对应「声明文件所在仓 git toplevel 之下」
  的实际 checkout。判定方式：枚举嵌套 checkout（深度 ≤3，剪枝 `node_modules`/`.venv`/
  `dist`/…），逐个 `deriveRepoIdentity` 后与 source 比对。
- **(b) `archived: true` 成员**：只校验两件事——① 库文件存在；② **不**满足 (a)
  （满足 (a) 却标 archived ⇒ 声明错误，拒绝 + warn）。

会话仓自身出现在 members 中则**剔除**（不报错——自列是冗余，不是危险）。

### 3.1 枚举只用于校验，绝不用于发现

**这是本判据与被否决的「自动探测嵌套 .git」之间的全部差别。**
`worktreeSources()` 的返回值只回答「这个**已声明**的成员是不是真在这儿」，
**永不被迭代出来当成员**。未在 `members` 里写出的仓库一律不生效。

否决自动发现的理由：它把「本会话能读谁的记忆」变成**磁盘上碰巧有什么**的函数，
而磁盘内容是攻击者（或一次手滑的 `git clone`）可控面。
代码注释里对此写了明确警告——因为这两个循环长得一样，却回答相反的问题。

### 3.1.1 `.git` **文件**必须验 gitdir 落点（第二轮补的安全边界）

`.git` 在普通克隆里是目录，在 worktree/submodule 检出里是**文件**，内容为
`gitdir: <路径>`。**该文件随仓提交，与 `.strataloom-group.json` 是同一个
攻击者可控面**——一次 `git clone` 同时带来两者。

攻击构造：把工作树内某目录的 `.git` 文件指向**工作树外**的 gitdir。
此时 `git rev-parse --show-toplevel` 会**如实**返回工作树内的路径，于是该仓
通过准入规则 (a) 被当作**工作树成员**准入，审批提示把一个位于别处的私有仓库
描述为「(checked out inside this workspace)」——**唯一能让人做判断的
ARCHIVED 警告根本不出现**。

⇒ 判定不再只看 `.git` 这个名字：`.git` 为文件时解析其 gitdir，
经 `realpath` 后必须落在 workspace 之内，否则不计为「工作树内 checkout」。
用例 15 锁住这条（并端到端断言此种成员被规则 (a) 拒绝、不惊动人）。

符号链接不是第二个洞：`entry.isDirectory()` 对 symlink 返回 false（已验证），
且本判定同样解析链接目标。

### 3.2 `archived` 是人的断言，代码无法验证——承重的是审批

`archived` 字面主张的是「本机任何角落都没有该 checkout」。**代码验证不了这件事**
（要扫全盘，且下一秒就可能被 clone 出来）。谓词层只验证了「有库 + 不在本工作树内」。

**因此承重的安全闸是审批，不是这个谓词。** 审批提示**逐条列出**每个 archived 成员
并标注该主张不可验证，因为这是唯一一个「人能看到『这个组会读一个本仓之外、无 checkout
的库』并说不」的地方。

如实记录一个**设计使然**的行为：标了 `archived:true` 的 `strataloom` 库
（有库、不在 FullStack 工作树内）**在谓词层会通过**。测试 7b 就是这么写的——
断言它**通过谓词**、被**逐条呈现给人**、且未审批时**零参与**。
不假装谓词拦住了它。

### 3.3 承重闸的直接后果：`approval` 策略为 `never` 时本功能**整体不可用**

**实测（2026-09-01，发布安装后当场发现）**：会话审批策略由 `ask` 改为 `never` 后，
平台 `dsh-user-approval` 的 `decide()` **不询问任何人，直接返回 `'rejected'`**：

```js
// @deepseek-ai/dsh-user-approval/lib/index.js:188
if (this.effectivePolicy(session) === "never") return "rejected";
```

而 `service.ts:248` 要求 `outcome === 'allowed-once'` 才放行，于是 `groupMembers()`
返回 `[]`，会话退化为只读本仓——与未声明组时逐字节一致。

**这是正确行为，但有一个反直觉的后果，必须写下来**：

> 把审批调成 `never`，**不是**「跳过审批直接放行」，而是**永久拒绝**。
> 用户若为了少被打扰而设 `never`，得到的是**功能静默失效**，而日志只有一行 `info`。
> 策略名的字面读法是 "never ask"——它 never asks，**因而 never grants**。

**不为此加例外。** 理由与 §3.2 同源：审批是本功能唯一的承重安全闸（`archived`
谓词验证不了它声称的东西）。「策略为 never 时自动放行」等于让**关掉安全提示这个动作**
去**授予**它本该守住的权限。宁可功能不可用，也不要一个在没人看着时自己放行的闸。

**排障判据**：组没生效时先查审批策略，再查声明文件。日志
`group "<name>" was not approved (rejected)` 里的 `rejected`（而非 `unavailable`）
就是「策略为 never」的指纹；`unavailable` 才是「审批服务缺失」。

## 四、实现要点与被否决的写法

| 位置 | 做法 | 为什么不那样做 |
|---|---|---|
| `readableStores()` | **一行未改，仍 private** | 它是 4 个消费者的共用定义，其中 `forget` 要的是「可**写**的库」。扩它 = 悄悄把读特性变成跨仓写权限 |
| `forget()` | **显式钉死** `readableStores()` + 长注释 | recall 带 id 返回（`withId=true`），读泄漏会直接转化为写破坏能力。该注释是防止未来「顺手统一」的唯一防线 |
| `source()` | 跟随 recall 扩大 | 它是 recall 的一个 MODE；能召回却不能下钻证据 = 有主张无出处，违反 D3 |
| `list()` | **按库分列**，`MemoryScopeListing.scope` 扩为可携带成员标识 | 混在一栏下等于用完整性换掉可辨性，而唯一提供的动作（forget）对外仓是拒绝的 |
| `projection.ts` | **未改** | 全部 7 个库 `team-shareable AND human_confirmed=1` **合计 0** ⇒ `projectStore` 恒走 `rmSync` 分支；声明文件放进 `.repo_memory/` 会被下次 share 删掉，且违反 ADR 0001「该目录永不作为输入」 |
| `tools.ts` `parameters` | **未加仓库参数** | 模型不得声明 scope（D1） |
| 外仓 `usage` | **不写**（§2.4） | 跨仓时 usage→decay→`memories.status` 会穿透 D4；且它让审批提示语成为不实陈述 |
| `recall/inject.ts` | 仅为归因动（§2.5）：新增 `FRAMING_HEADER_MIXED` + 抬头二选一 | 本轮唯一破例。无组时渲染**逐字节不变**，注入路径的包内容与预算**逐条不变**（用例 18b / ADR 0007 加载期守卫仍绿） |
| `recall/render.ts` | `RenderableHit.source` **可选** | 缺省即「本仓」，于是所有旧读出口天然零变化——不是靠传参记得对，是靠结构 |
| 读路径取库 | 只 `stores.get()` | `openAllKnown()` 激活时已扫开磁盘上全部库（孤儿库也在内）；`open()` 会 mkdir+migrate，等于**让声明文件凭空造库** |
| 授权存储 | 进程内，键 = `(会话仓 source, members 指纹)` | **绝不存进仓库**：信任决定存在攻击者写得到的地方就不是信任决定——签入的授权文件等于让任何能发 PR 的人给自己预授权 |
| 审批服务缺失 | **整体关闭**（fail closed） | 不同于 `llm`（缺了只是不自动抽取），审批是声明文件与「读别人的库」之间唯一的闸 |
| 声明失效 | 重启生效，不热重载 | 热重载会在审批与生效之间开 TOCTOU 窗口 |

**TOCTOU 处理**：读一次内容 → 算指纹 → 查授权 → **用同一次内容**（与 §2.1 迁移
「校验必须在锁内」同型）。测试 9 在审批后篡改声明文件，断言本会话仍用审批时那一份。

## 五、`RECALL_FOREIGN_BUDGET_TOKENS` = 220：一次被自己的守卫证伪的定值

**这一节是本轮最值得记的过程。**

### 第一次定值：150（实测拐点）

在 1412 个机械生成的种子上 replay，经 `renderFramed(withId=true)` 出口计数：

```
预算   单条可容纳率      获得外仓内容的种子    外仓投递条数
 50     0/59 ( 0.0%)         0/1412                0
100     6/59 (10.2%)       174/1412              178
150    53/59 (89.8%)       848/1412             1079
200    59/59 ( 100%)       898/1412             1186
300    59/59 ( 100%)       900/1412             1378
500    59/59 ( 100%)       901/1412             1540
```

150→500 投递涨 42.7%，但**获益查询只涨 6.3%**——过了拐点，多出的预算只是把已服务的
查询变长。于是取 150，理由写得很像回事。

### 守卫当场否决：150 装不下一个最坏 L2 块

新加的加载期守卫立即抛错：

```
RECALL_FOREIGN_BUDGET_TOKENS (150) cannot admit even one worst-shaped
foreign row (194 tokens rendered with its id)
```

**守卫是对的，实测是不完整的。** 实测只看见了**已经存在**的 59 行，看不见写路径
**被允许创建**的行：成员库的 L2 块按 `ROLLUP_TITLE_TARGET_CHARS + ROLLUP_TARGET_CHARS`
写入，按 recall 的尺子（带 id、换行缩进）定价是 **194 tok**：

```
最坏 L2 块  withId=false（注入的尺子）  183
最坏 L2 块  withId=true （recall 的尺子） 194
```

在 150 下，一个只有场景块的成员库返回**零**——`withinBudget` 对超限行整条跳过，
所以不是部分退化而是**全无**。**功能开着、审批过了、结果恒空**，正是 ADR 0007 教训 4
（测试全绿 + 守卫绿灯 = 零产品效果）的又一个实例。

其实 p90=151 已经露在 150 之上，数据里看得见，我仍选了拐点——因为「89.8% 的行装得下」
听起来像拿到了大部分价值。**不是的**：装不下的那 10.2% 恰恰是派生行，即一个外仓
「内容多到需要摘要」之后贡献的**主要**东西。

### 定案：`max(拐点, 最坏被强制行) = max(150, 194)` → 200

代价在同一批种子上量了：外仓投递 1079→1186（+9.9%），获益查询 848→898（+5.9%），
渲染均值 266.2→280.3 tok（+5.3%）。**本仓侧在任何取值下都不受影响**（1401/1401 逐条相等）。

> **教训**：`RECALL_FOREIGN_BUDGET_TOKENS` 的实测口径是「今天库里有什么」，
> 而守卫的口径是「写路径允许产生什么」。**两者都必要，且后者不能由前者代替。**
> 这与 ADR 0007 教训 2「asked for ≠ enforced」是同一族错误的镜像：
> 那次是把「请求」当成了「强制」，这次是把「现存数据」当成了「可能数据」。

### 5.0 第三轮再定案：加来源标注后 200 → 220

QA 端到端发现 recall 结果**不带来源标注**却挂着「in this repository」抬头（阻断 3），
修法是每条外仓条目渲染 `(from <source>) `。该标注**进入定价**，最坏行从 194 涨到 212，
**加载期守卫当场再次否决 200**：

```
strataloom: RECALL_FOREIGN_BUDGET_TOKENS (200) cannot admit even one
worst-shaped foreign row (212 tokens rendered with its id)
```

于是 `max(150, 212)` → **220**。同一守卫链条第二次以同样方式生效，这是它该有的样子。
`GROUP_MAX_MEMBERS = 6` 被**重新解**了一遍（不是沿用）：6 → 7939 字符（余 253，原为 763），
7 → 8874 抛出。余量变薄是标注的真实代价，如实记录——**下一次条目形状变宽就会把它压到 5，
而说出这句话的应当是守卫，不是读者。**

### 5.1 本节论证的一处**证伪与订正**：194 的口径不代表真实 L2

**上面「最坏 L2 块」的推导过程与现实不符，如实更正。** 194（现 212）来自
`worstShapedBody(ROLLUP_TARGET_CHARS = 620)`，即**写路径今天允许产生的**最大块。
但 `rebuild.ts:272` 的 `.slice()` 钳制是**后加的**，库里的存量 L2 全是钳制前的旧数据。
实测 7 个真实库（**只读**打开，2026-09-01）：

| 口径 | 数值 |
|---|---|
| active L2 块 | **17** 条 |
| body 字符 | min 317 / p25 677 / p50 773 / p75 1100 / **max 1820** |
| **超过 `ROLLUP_TARGET_CHARS=620` 的** | **15/17**（88.2%） |
| 按 recall 尺子（带 id + 来源标注）定价 | min 109 / p50 **222** / max **496** tok |
| 装得进 200 | **5/17** |
| 装得进 220（本轮定值） | **8/17** |

即**真实 L2 的中位数就已经超过预算**，93.3% 的外仓 L2 候选在种子回放中被预算丢弃。
所以第二节那句「最坏 L2 块 194 tok」描述的是**未来可能产生的块**，
**不是**库里现有的块——原文把两者混在一句话里论证，读起来像是「200 足够装下 L2」，
**而实测恰恰相反**。

**但结论值仍然成立，理由与原文不同**，必须写清楚，否则后人会基于假前提去调这个常量：

1. **外仓投递的主体是 L0/L1，不是 L2。** 实测 active L1 = **295** 条，
   cost p50 162 / p90 200 / max 441，**292/295（99.0%）装得进 220**；
   L1:L2 在外仓投递中约为 **1564:80**。覆盖率由 L1 决定，而 L1 覆盖是满的。
2. **预算不能靠「装下存量 L2」来定**：它上有天花板——
   `RECALL_FOREIGN_BUDGET_TOKENS` 一涨，`GROUP_MAX_MEMBERS` 就得降
   （220 时余量已只剩 253 字符）。要装下 max=496 的那条，成员数会掉到 3 以下，
   **拿一条摘要换掉一半成员位是明显的负交易**。
3. **存量超限块会自然消解**：钳制已在写路径生效，重建会用钳制后的块替换它们。
   为一批**正在消失的旧数据**调常量，是把临时状态写进不变量。

> **教训（与上一条互补）**：上一轮的错误是「拿现存数据当可能数据」；
> 这一轮暴露的是它的**镜像**——**拿可能数据当现存数据**去描述覆盖率。
> 守卫必须按「写路径允许产生什么」定价（这没错），
> 但**文档不能因此声称现存数据也长这样**。两个口径都要写，且要分别标明。

守卫刻意用**带换行**的 body 定价（`worstShapedBody`），不用 `'x'.repeat(n)`：
`renderEntry` 会把 `\n` 缩进成 `\n␣␣`（每换行 +2 字符），单行合成 body 对这个维度
完全失明——正是 ADR 0007「换行盲区」记录的假绿灯。测试 10 断言 shaped > flat，
否则该用例什么也没证明。

### 5.2 第二轮订正：原来那个守卫是**恒真**的，`GROUP_MAX_MEMBERS` 从 8 改为 6

上一轮此处写着「`GROUP_MAX_MEMBERS = 8` 让最坏容器在加载期可定价
（`500 + 8×200`）」，并在 `constants.ts` 注释里称底部断言会检查它。
**这是不实陈述**，如实更正：

```ts
// 旧守卫
if (worstGroupRecallTokens > RECALL_RESULT_BUDGET_TOKENS * (GROUP_MAX_MEMBERS + 1))
```

展开即 `500 + N·200 > 500·(N+1)` ⟺ `N·200 > N·500` ⟺ **`200 > 500`**。
**N 被完全约掉**，条件恒为假。实测把 `GROUP_MAX_MEMBERS` 改成 `100000`
（最坏 20,000,500 tok），模块**照常加载、全套测试全绿**。
**假守卫比没有守卫更坏**：它让人以为这个问题已经被问过了。

更根本的错误是**它比较的不是一个容器**。`RECALL_RESULT_BUDGET_TOKENS × (N+1)`
不对应运行时任何东西——运行时**不存在** 2100 的容器。这正是 ADR 0007 教训 1
（守卫必须建模运行时真正争用的容器）被违反。

**真正的容器是渲染出来的那个字符串，单位是字符。** 顺着模型实际收到的值往外追：

```
service.recall()            → hits（结构化）
tools.ts output.render()    → content: [{ type:'text', text }]
dsh-agent-loop              → appendToolResult(..., result.content)   lib/index.js:302
dsh-llm createToolResultMessage → 只把 content 放进消息            lib/index.js:202
```

`createToolResultMessage` **只**装 `content`，结构化 `value` 永不进模型。
所以渲染串就是全部产物，而下游第一个截断它的是平台的 tool-result pruner——
在 `@deepseek-ai/dsh-base/cordis.patch.yml` 与全部三个 agent preset 中均配置为
**`thresholdChars: 8192`**，超限即保留 head 4096 + marker + tail 1024，**删掉中间**。

按旧常量（`500 + 8×200`）构造最坏包实测：

```
渲染包        8506 字符   403 条
经 pruner 后  5159 字符   231 条
静默删除                  172 条
```

⇒ 新守卫建在 `tools.ts`（**紧邻它所约束的那次 render 调用**，且方向上避开
`constants → inject → constants` 循环），用**真实 `renderFramed`** 构造最坏包并
比对 `RECALL_PACKET_MAX_CHARS = 8192`。该守卫**会绑**：

| 成员数 | 最坏包字符（预算 200） | 最坏包字符（预算 220，本轮） | 结果 |
|---|---|---|---|
| 5 | 6579 | 7004 | 通过 |
| **6** | **7429（余 763）** | **7939（余 253）** | **通过** |
| 7 | 8279 | 8874 | **抛出** |
| 8 | 9129 | 9809 | **抛出** |

所以 `GROUP_MAX_MEMBERS = 6`——它是**解出来的**（能装下的最大值），不是挑的。
真实动机场景声明 3 个成员，仍有 2× 余量。**常量跟随不变量走**（ADR 0007）。

守卫填充用的**不是**上面那个 worst-shaped 行：那个行最大化 **token**，
而这个容器的单位是**字符**，二者的最坏对手相反。`estimateTokens = ceil(len/4)`，
故 c token 的条目最多 4c 字符，且该上界**可达**（16 字符 = 4 token，
恰是条目的最低成本）。用它填满预算即得字符数上界。

> **已知耦合，如实记录**：8192 是本包不拥有的平台默认值，若部署方调低
> `thresholdChars`，此守卫会偏乐观。但它仍严格优于被替换的那个——
> 后者建模的容器根本不存在；且守卫**定价的是真实渲染包**，会漂移的只有阈值本身。

用例 10b 断言「N+1 必须溢出」（上界必须是**紧的**），
用例 10c 更进一步：**真的加载**一份把 `GROUP_MAX_MEMBERS` 改大的副本，要求
**加载即抛**。这是唯一能抓住「条件恒假」的断言——把旧公式放回去，10b 仍全绿，
**只有 10c 变红**。

## 七、明确不做

1. 不做跨库注入（任何形式）；2. 不做跨库 forget／任何跨库写；
3. 不改 `.repo_memory/` 语义、不往其中放输入；4. 不给 `memory_recall` 新增仓库参数；
5. 不做自动探测嵌套 `.git`（枚举**仅**用于校验声明）；6. 不做双向声明；
7. 不读组内其他仓的声明文件（单向、单文件、不传递）；8. 不做运行时失效/热重载；
9. 不做跨库 rank 归一化（单点命中无方差，归一化无定义）；10. 读路径不 `open()` 新库；
11. 不为组新增任何排序/权重旋钮——**排序不可由声明文件影响**，否则把策略交给了
    攻击者可控面。

## 八、如实记录的残余问题

- **孤儿库的 33 条记忆仍然删不掉，但也不再被写。** 第三轮之前，本会话的纯读
  会给它写 usage 并（经 decay）延长其 active 期——一个本机已无 checkout 的库，
  被另一个仓的活动续命。现已删除该写入（§2.4）。至于「删不掉」： `NFBY_CMS_Ops` 无 checkout，而 forget 只作用于
  会话所在仓库，所以在 FullStack 会话里读得到、删不掉。拒绝信息对此**明说**
  （测试 6b 锁住这句话）。这是改名分裂的既有事实，**本方案不用跨库写权限去补偿它**
  ——那会把一个数据清理问题换成一个权限模型缺口。
- **`archived` 谓词弱于其字面含义**（见 §3.2），承重的是审批提示。
- **审批策略为 `never` 时本功能整体不可用**（见 §3.3）：`decide()` 直接返回
  `'rejected'`，组退化为只读本仓。这是承重闸的必然推论，不打例外。
- **授权只存在于进程内存**（`Set`，键 = `(会话仓 source, members 指纹)`），
  **不落盘、不跨进程持久化**：dsh 重启后必须**重新审批**，磁盘上不存在任何授权文件
  （已核：`~/.dsh/strataloom/` 下除 `*.sqlite*` 外无文件）。这是**有意付出的代价**——
  信任决定若存在攻击者写得到的地方就不再是信任决定。它与「声明不热重载」是同一个
  决定的两面。
- **member source 现在过 `normalizeSource`**（与 `deriveRepoIdentity` 同一条规范化
  规则），因此 `.git` 后缀／大小写主机名／尾斜杠不再静默失配。此前一个远端的六种
  写法会派生出六个键、六次「库不存在」warn。失配方向本就是**读不到**而非读错，
  故非安全漏洞，但看起来与功能损坏无异。用例 16 覆盖最常见的 `.git` 后缀写法。
- **`worktreeSources` 的深度上限 3 与剪枝表是成本折中**，不是安全边界：
  一个埋在第 4 层的成员会被判为「不在工作树内」并跳过（带 warn），
  用户可改标 `archived:true`——那条路径会走审批，由人来看。
