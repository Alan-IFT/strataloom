# 0003 · 「不确定是否长期有效时先问」由引导实现，不建机制

- 日期：2026-08-23
- 状态：已采纳
- 相关：阶段 1、`GUIDANCE_SECTION`、D10

## 背景

4×4 原始设计要求：「是否长期有效或目标不清楚时，Agent 会先询问。」

直觉做法是在 `memory_propose` 里加一条询问链路：判定候选是否可疑 → 调
`ctx.userQuestions.ask()` → 按答复决定写不写。

## 决定

**不新增任何机制。**在引导段加一句「无法判断是否长期有效时，先问，不要猜」，
询问由模型调用平台既有的 `ask_user_question` 工具完成。

## 理由

1. **能力已经存在**：harness 自带 `dsh-tool-ask-user`，模型本就能发问。
   在 `propose` 内再建一条询问路径，是把已有能力实现第二遍——本项目
   D7–D9 三次事故的同一形状。
2. **判据只能由模型给出**：「这条是否长期有效」是语义判断，代码无从计算。
   若加机制，机制本身仍要问模型，只是多绕一层。符合既有原则
   「模型智能优先于代码，代码掌握权限/事务/安全边界」——询问不属于后者。
3. **写路径不应被阻断**：`propose` 是同步单事务写入。插入一次等待人类
   答复的往返，会引入超时、取消、答复迟到等新失败模式，而这些都发生在
   一个本可无状态完成的写入里。
4. **少即是多**：新增软依赖 + 判定逻辑 + 三条失败路径 ≈ 数十行，换来的
   能力与一句引导相同。

## 代价（如实记录）

- 是否发问取决于模型是否遵循引导，**没有代码强制**。
- 若日后观察到模型频繁静默存下不确定的内容，可用 §9 metrics 采集
  「低价值记忆占比」，**有数据再考虑**是否需要强制机制——而不是现在预设。

## 替代方案

- *在 `propose` 内建询问链路*：见上，被四条理由否决。
- *让 `propose` 对可疑候选返回"需澄清"而不写入*：仍需代码判定何为可疑，
  等于把语义判断塞进代码；且模型完全可以在调用前就发问。
