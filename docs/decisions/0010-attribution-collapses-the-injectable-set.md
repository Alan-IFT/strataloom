## 一、事实：两条各自正确的规则，交互后掏空了注入集

读路径上有两条独立规则：

```
写侧  extract.ts:271   provenanceFor(sourceSeqs, bySeq)   ← 取被引来源的【最低信任】
读侧  types.ts:126     INJECTABLE_PROVENANCE             ← 只放行 human/principal-explicit/parent-agent
      fts.ts:61        queryInjectableSet ... provenance IN (...)
```

两条都有明文设计理由，且**单独看都是对的**：

- 最低信任传播是 §2.4 的 fail-closed，防的是「工具结果混进一条记忆，却被当作
  人说的话」——这是**注入安全**边界，ADR 0008 曾专门加固（把转写改成 JSON，
  使工具输出无法伪造 `[user]` 行）；
- 「`subagent`/`tool-output` 仅工具召回、绝不默认注入」是 §2.3 的离散规则。

**交互后果没有被任何一处量过。** L0 里 `tool-output` 是绝对多数（strataloom 库
1924/3027 = 63.6%），于是任何一条引用了工具输出的候选记忆——**哪怕它同时引用了
人的原话**——都被打成 `tool-output`，随即被读侧永久排除。

**全库实测（7 个 repo 库，2026-08-31）**：

```
                     可注入 / 总数     可注入率
管线（extract）产出     26 / 238        10.9%
人工（propose）产出     60 /  61        98.4%
```

**对照组是决定性的**：`propose` 走 `principal-explicit`，不经 `provenanceFor`，
可注入率 98.4%。**同一个注入过滤器，对两类写者的结果相差 9 倍**——所以问题不在
过滤器的阈值，而在归因把管线产出整体压到了阈值之下。

> **逐库读数**（避免 ADR 0009 教训 5 的单样本陷阱）：管线产出为 0 的三个库
> （Ops/Frontend/Backend）纯 propose，故 100%；有管线产出的四个库分别是
> `2631a175` 0/17、`5ed2b4d2` 10/122、`94394b03` 15/82、`aafbf0fa` 1/17。
> **四个库全部低于 20%，无一例外**——不是某个库的偶然。

## 二、ADR 0008 加剧了它，而当时没有量到这个出口

按重启时刻（2026-08-30 12:50:41 UTC）切分**全库管线产出**：

```
0.3.6 前   可注入  24 / 180  = 13.3%
0.3.6 后   可注入   2 /  58  =  3.4%
```

机制清楚：ADR 0008 让 `tool-call:` 行进入 L0，**工具类供给进一步变大**，候选
引用到工具行的概率上升，归因下沉更频繁。

**这不是说 ADR 0008 做错了。** 它采集「agent 做了什么」的收益是真实的，本文
第四节确认那批行确实被引用。**它错在测量停的位置**——与 ADR 0009 §八教训 1
完全同型：ADR 0008 量了「事件总数 +11.7%、孤儿率 100%→1.2%」（采集出口），
量了「被引段 55.9% 来自工具结果」（选材出口），**唯独没有量「产出的记忆里有
几条能进注入包」**（用户出口）。

> 它甚至在否决 M8 时写下了正确的判据——「它把 §2.4 的**安全**分级挪用为
> **信息价值**分级」——但只把这句话用在**选材侧**（要不要按 trust 排序选材），
> 没有回头查**归因侧**正在做同一件事。**同一个错误形状，在同一篇 ADR 里被
> 指认了一次、又被漏掉了一次。**

## 三、派生层救不回来——它继承同一个过滤器

一个自然的指望是「L2 会把这些记忆汇总进去」。**不成立**：

```
rebuild.ts:79   packetOverflows   ← queryInjectableSet(store, ROLLUP_SOURCE_LIMIT)
rebuild.ts:164  rollup 的输入      ← queryInjectableSet(store, ROLLUP_SOURCE_LIMIT)
```

**触发条件与输入都读同一个过滤器**，所以那 212 条对 L2 同样不存在。

这直接解释了两个活跃库派生层为空——**此前可能被误读为「管线坏了」**：

```
库            active raw   可注入   计价 tok   阈值 1300   L2 块
5ed2b4d261b2     105          6       1118     不溢出       0
94394b03d790      66         13       1079     不溢出       0
```

**不是管线坏了，是分母被掏空了**：105 条记忆只按 6 条计价，自然永远不溢出，
于是永远不入队 rebuild。**一个为「记忆太多」设计的触发器，被「记忆都不算数」
关掉了。**

## 四、分解：本文初稿在这里犯了它自己批评的错误（已作废并更正）

> **⛔ 本节初稿的分解已作废，不要引用它。** 更正记录保留在此，因为**错误的
> 方法比错误的数字更值得留档**。

初稿从 `evidence.excerpt` 反解每条记忆实际引用的 L0 行，得出
`已可注入 26 / A 混合来源 78 / B 纯低信任 126 / C 引文全高信任却被排除 8`，
并据此断言「改归因只能把 10.9% 提到 43.7%」。

**该分解不可用**，因为它读的不是证据，是**证据的截断产物**：

```
全库 evidence n=241，excerpt 长度分布（2026-08-31）
  0-99: 1   100-199: 9   200-299: 4   300-399: 9   恰好 400: 218
  即 90.5% 被截断，211+ 条精确堆在 400，无自然长尾——这不是分布，是一堵墙
```

`extract.ts` 当时把 `.slice(0, EXTRACT_EVENT_EXCERPT_CHARS)` 施加在
`join('\n---\n')` 后的**整串**上，于是一条引用多个来源的记忆，**第二段起被
routinely 截掉**。反解只看得见前 400 字符，低信任来源恰好是被切掉的那部分。

**「C 类 8 条」尤其是纯粹的假象**：8/8 的 excerpt **恰好 400 字符**。它们不是
「引文全为高信任」，而是「只有高信任那段活了下来」。初稿据此推断出一个不存在
的实现矛盾，还差点把它当作修法依据。

**可判定样本只剩 14 条**（A 类未截断 11、B 类未截断 3），不足以支撑任何分解。

**方向仍是单一的**：截断只会隐藏低信任来源，不会凭空造出高信任来源。所以
**第一节的主结论不受影响**——它由 `propose` 98.4% vs 管线 10.9% 的**对照组**
独立支撑，完全不依赖 excerpt。**垮掉的是修法依据，不是缺陷本身。**

> **这正是本文第八节教训 1 的形状，而本文自己撞了上去**：一条读路径上有
> 两把尺子（归因的过滤 + 证据的截断），初稿只量到了内侧那把。
> **在一篇批评「量到中间产物」的 ADR 里，把中间产物当成了最终证据。**

**因此重新分解的前置条件是先修 excerpt 截断**，否则任何分解都会重蹈覆辙。
该修复已于 2026-08-31 完成（见 §六），**A/B 的真实比例须在修复后重新采集**
——用修复前写入的 218 条历史行去分解，得到的仍是同一个假象。

### 初稿据 C 类推出的「实现矛盾」不存在——那是截断的假象

初稿曾断言：`provenanceFor` 把无法解析的 seq 计为 `tool-output`，而 `excerpt`
用 `.filter(cited => cited !== undefined)` 把它静默丢弃，两个消费者对同一份
`sourceSeqs` 的缺失语义不一致，导致「证据与归因互相矛盾」。

**该推论已被证伪。** 那 8 条记忆的 excerpt **全部恰好 400 字符**，其低信任
引文是被**整串截断**切掉的，不是被 `.filter()` 丢弃的。初稿举的那个实例
（`memory_recall/memory_propose bug…`，excerpt 只见 `[user]` 而 provenance 为
`tool-output`）正是一条 400 字符的截断行。

**两个消费者的缺失语义确实不同，这一点属实**（`provenanceFor` 计入、`excerpt`
丢弃），但**它不是那 8 条记忆的成因**，也没有任何观测证据表明它曾真实发生过
——要触发它，模型必须给出一个转写窗口里不存在的 seq，而现有数据无法区分
「发生过但被截断掩盖」与「从未发生」。**故降级登记为「理论可能，未观测」，
本轮不据此改代码。**

> **教训**：初稿为一个**由截断制造的**现象，编造了一个**结构性**解释，而且
> 那个解释在代码里确实找得到对应物——这让它更可信，也更难被推翻。
> **能在代码里找到一个说得通的机制，不等于它就是眼前这批数据的成因。**

## 五、为什么测试全绿

`npm run verify` **171 passed / 0 fail**（2026-08-31 实测）。三个原因：

1. §2.4 的「映射全覆盖」测试断言的是**未知类别 ⇒ tool-output**——即它**正是
   在锁定**本文指出的降级行为。测试通过，说明实现符合规范；**规范本身没有
   回答「降级后还能不能被使用」**。
2. 注入测试断言「`tool-output`/`subagent` 永不默认注入」——同样在锁定读侧规则。
3. **没有任何测试跨越这两条规则**去断言「管线产出的记忆最终有多少能进注入包」。
   两个端点各自被覆盖，**中间的乘积无人测量**。

> 与 ADR 0009 教训 7 同型：**测试覆盖的是各自的假设，不是产品的契约。**
> 这里更微妙——两个测试都是对的，**它们的合取才是缺陷**。

## 六、决策：先修证据，再谈归因（本轮已完成第一步）

归因的修法涉及一个**产品判断**而非参数，且**当前没有可信分解支撑它**（§四）。
所以本轮**只修使分解不可信的那件事**，归因原样不动。

### 本轮已实施：excerpt 的每事件配额（2026-08-31）

**根因是 D7–D9「一条规则两处实现」的第四个实例**：
`EXTRACT_EVENT_EXCERPT_CHARS` 的文档语义是**每事件**上限
（"Per-event excerpt cap"、"extraction cuts every event to this"），
`renderTranscript` 一直这样用，而写 evidence 时它被施加于 join 后的**整串**。

同时修掉一个**被它意外掩盖的独立缺陷**：`sourceSeqs` 从无长度上界
（同一个 `parseCandidates` 里 `candidates`/`title`/`body` 都有 `.slice()`，
唯独它只过滤类型）。这使 `worstExtractReplyChars()` 守卫**在假设一个从未被
强制的界**——实测破裂点 `N=11`（`5300 + 6717 = 12017 > 12000`，余量仅 18）。

> **归因限定**：`maxTokens` 是否把输入计入**取决于 provider，本插件不可见**。
> 故后果应表述为「**在按整个 exchange 计价的 provider 上**，回复被截断 →
> 非 `stop` 的 finish 判为失败 → 重试 → 最终 dead-letter」，**不是无条件必然**。

修法要点（全部经方案评审、代码审查、QA 三方独立验证）：

- **约束输入而非二次截断输出**：给 excerpt 加总量 cap 是**对同一根因的第二次
  绕行**，仓库判例已写死（`ROLLUP_TRANSCRIPT_CHARS`：*"capping the output again
  would work around the same root cause a second time; bounding the input
  removes it"*），且**救不了 exchange 守卫**。
- **不新增常量**：复用既有的 `WORST_SOURCE_SEQS`，把它从「守卫的假设」变成
  「写者的强制」，使守卫定价的形状与代码允许的形状**成为同一个数**。
- **顺序 filter → dedupe → slice 不可交换**：先截断会让 10 个重复 seq 挤掉
  10 个不同来源。该顺序**由测试强制**，非靠注释维持（交换顺序即变红）。
- **去重对归因可证明无损**：`provenanceFor` 取最小优先级，min 幂等；空数组
  由前置分支先行返回。已由差分测试与真实 `runExtractJob` 双重锁定。
- **只截 text，`[label]` 整体保留**：截断 label 会产生 `[tool:ba` 这类无法
  归因的段——**破坏归因的截断比缩短引文的截断更糟**。

**不回填历史**：被截断的字节不可恢复，且 `evidence` 表**根本没有存
`sourceSeqs`**，连「这条记忆引用了哪些 seq」都已无法恢复——**回填在技术上
不是「选择不做」，而是做不到**，任何回填都只能是重新猜测。L0 原文仍在
`conversations`（90 天），人工核对原话的路径未断。

### 下一步（未排期）

- **重新采集 A/B 分解**：必须用**修复后新写入**的 evidence，历史 218 条仍是
  截断产物。
- **再评审归因修法**：放宽最低信任传播会削弱 §2.4 的 fail-closed，而那正是
  ADR 0008 加固过的注入安全边界。**放宽前须先实测证明伪造路径已被 JSON
  转写堵死**——这是可证伪命题，应当实测而非推断。
- **B 类的产品判断**：「工具输出里提炼的工程教训是否该默认注入」。§2.3 现行
  答案是「不该」。若不变，则**该改的是期望值**——承认管线主要产物是**召回
  可用**而非**注入可用**，并据此重估 L2 触发器的分母。

## 七、附带发现（不在本轮处理）

## 八、教训

1. **两条各自正确的规则，其交互可以是缺陷。** 本例的两条规则都有明文设计
   理由、都有测试锁定、都在评审中被讨论过——**缺陷只存在于它们的乘积里**，
   而没有任何一方的测试会看到乘积。
2. **量到用户出口这件事，要在每次改动后重做，不是做过一次就完了。**
   ADR 0009 立了「量到最外面那把尺子」，ADR 0008 比它早一轮，**同一个仓库在
   相邻两轮里，一轮立规矩、一轮违反它**。规矩写进 ADR 不等于下一轮会被执行。
3. **对照组比绝对数更有说服力。** 「10.9% 可注入」单独看可以被解释为「提炼
   质量不高」；`propose` 98.4% 的对照把这个解释排除掉了——**同一过滤器、
   不同写者、9 倍差距**，指向的必然是写侧归因而非内容质量。
4. **当证据与它所证明的字段矛盾时，先怀疑证据的构造过程。** 本文初稿反过来
   了：它相信证据、去怀疑归因，于是为一个由**截断**制造的现象编造了一个
   **结构性**解释。**证据不是中立的记录，它也是一段有缺失语义的代码**——
   而这段代码恰好会隐藏导致矛盾的那个输入。
5. **一个「恰好」应当立即引发对测量工具的怀疑。** 8 条记忆的 excerpt 全是
   400 字符、211 条精确堆在 400——**这种整齐不可能来自内容，只能来自尺子**。
   初稿看到了这些数字却没有停下来问「为什么这么整齐」。**分布里的直角是
   仪器留下的，不是世界留下的。**
6. **能在代码里找到一个说得通的机制，不等于它就是眼前这批数据的成因。**
   初稿那个「两个消费者缺失语义不一致」的解释在代码里**确实存在**，这让
   错误结论更可信、更难推翻。**机制的存在性与它的因果作用是两个命题，
   要分别验证。**
7. **测量之前先确认「跑着的是哪个版本」，而这不等于「重启了吗」。**
   本文的修复发布为 v0.3.7 后，harness 于 **22:46:35** 重启、插件于
   **22:51:41** 落盘——两件事都发生了、都报告成功、「已重启」也是真话，
   而跑着的仍是上一版。**顺序错了，两个真陈述合成一个假结论。**

   该判据在本轮之前**已经以正确形式存在过**（`STATUS.md` 记 0.3.6 时写了
   「PID 3419287，晚于 0.3.6 落盘的 17:47:56」），但它被写成**对某次发布的
   事后记录**，而不是**下一轮开工前要执行的一步**，所以没能拦住重演。
   ——**与教训 2 同型：规矩写进文档不等于下一轮会被执行；只有写成一条要跑的
   命令、并放在开工第一屏，它才有约束力。**

   对**只改写路径**的修复，这一条尤其要紧：修复缺席时**不报错、不抛异常**，
   只是继续产出旧形状的行，而旧形状的行看起来就是普通数据。**没有任何东西
   会提醒你。**
