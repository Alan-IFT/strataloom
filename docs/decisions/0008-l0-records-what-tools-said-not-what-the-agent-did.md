## 起因：一条走错方向的调研

本轮原本要推进**阶段 4（检索融合）**。ADR 0005 规定的开工条件是「比率显著
**且** 抽读 L0 确认存在『未命中 → 改写查询 → 命中同一条』的实例」。

我先断言「查询串从未被采集，故该判据用现有数据永远无法求值」，并据此提议
往 L0 增采 `memory_recall` 的查询串。**该断言是错的，方案已作废。** 记在这里，
因为它错的方式比它本身更值得留存。

**纠正一：判据是可求值的。** 查询串完整存在于平台 session 日志的
`tool/call.data.arguments`。实测（`session-0e8da469`）：

```
memory_recall tool/call 事件数: 41
  arguments: {"query":"仓库根就是应用根","kind":"fact","sourceOf":""}
  arguments: {"query":"测试数量棘轮","kind":"fact","sourceOf":""}
```

按 `callId` 配对 `tool/call` 与 `tool/result` 后，**135 次调用全部配对成功**，
MISS→改写→HIT 的实例可以直接跑出来。我只查了插件自己的 8 个库就下了
「物理上不存在」的结论，而 `transcript.ts` 读的正是 `agent.session.events`
——数据一直在那里。

> 注意边界：`store/conversations.ts` 的模块注释声明 L0 存在正是为了**不依赖**
> 平台 session 日志（它会轮转、会被清理）。因此该路径只能用于**一次性调研**，
> 不得固化为常设诊断依赖。

**纠正二：比率那一半本身还没重新采集。** 按 v9（CJK bigram，`2575df0`）切分：

```
v9 之前: 302 次调用, 121 未命中 (40%)   ← 占样本 99%
v9 之后:   4 次调用,   2 未命中 (50%)
```

`STATUS.md` 早已写明「v9 之前的未命中率混入了分词损耗，不能直接用于该判断」。
**我引用的 29%–58% 有 99% 来自失效样本**，有效样本只有 4 次调用。所以阶段 4
的门禁不是缺另一半判据，而是**两半都还不成立**。

**纠正三：我提的「把请求与结果合并成一行」变体有安全缺陷。**
`memory_recall.query` **没有长度上限**（对比 `memory_propose` 有
`TITLE_MAX_CHARS=200`/`BODY_MAX_CHARS=2000`），而 `metrics.ts` 与
`inspect.mjs` 都用**前缀**匹配 `text LIKE 'No stored memories matched.%'`
统计未命中。合并后前缀变成模型完全可控的字符串：

- 未命中不再被计数 → 比率恒为 0；
- 若改成非前缀 `%…%` 规避，则一次 `memory_recall("No stored memories
  matched.")` 就能把命中伪造成未命中，**任意操纵阶段 4 的开工决策**。

而锁定该常量的回归测试（`layers.test.mjs:459`）锁的是**措辞**，锁不住
**前缀位置的语义**——测试会继续全绿。体积论据也反了：行占比 71% 但字节占比
仅 26%（未命中行恒为 27 字节），合并方案 **+4.2%** 比加一行 **+2.5%** 更贵。

## 真正的缺口

走错的调研撞上了一个更大的问题：**L0 的采集契约与它自己声明的职责不符。**

设计文档 §1 说 L0 是「原始对话与完整上下文」，用于「核对原话、时间、来源」。
实际它记录的是「工具说了什么」，而不是「agent 做了什么」。

`src/transcript.ts` 的 `collectTurnEvents` 有两处丢弃：

```ts
if (event.type === 'tool/call') {
  callNames.set(String(event.data.callId), event.data.name)
  continue                      // (1) 只取工具名，参数整体丢弃
}
...
if (entry !== undefined && entry.text.trim() !== '') out.push(...)
                                // (2) 文本为空的事件整条丢弃
```

`textOf` 只取 `type === 'text'` 的块，所以一条**纯 tool_use 的 assistant 消息**
经 (2) 被整条丢弃。

**实测（`session-43422ed9`，本仓库自身的真实会话）**：

```
assistant/message 事件: 722   其中有文本 341   纯工具调用 380 → 被丢弃 52.6%
tool/call  事件: 863  → 100% 被丢弃
tool/result 事件: 878 → 全部入 L0
```

> **更正一处我先前的夸大**：我曾说「L0 丢弃 99.9% 的 assistant 事件」。
> 那是把两类库混为一谈得出的。按库实测，assistant 占 L0 的比例是
> **1.0%–45.9%**：低的两个库（`3e857510`=1.1%、`edf7a686`=1.0%）是
> **外部导入的单会话**，不是本插件正常采集；正常采集的库（`5ed2b4d2`=32.0%、
> `aafbf0fa`=28.1%、`94394b03`=25.9%）assistant 采集**工作正常**。
> 真实丢弃率是 **assistant 52.6% + tool/call 100%**，不是 99.9%。
> 这仍然是重大缺口，但数字要诚实。

**为什么这比查询串重要一个量级**：

1. **extract 的输入就是这些事件**。它在**看不见 agent 任何一次工具调用**的
   情况下提炼记忆——只看得见工具返回了什么，看不见为什么调用、用什么参数。
2. **孤儿结果**：L0 里每一条 `tool:<name>` 结果都没有对应的请求行。
3. 见下方「更正二」：本文原先在此处写的第 2 条（`parent-agent` 供给腰斩）
   **是错的**，已删除。

> **更正二（2026-08-31，方案审查实测）：`parent-agent` 的供给从未腰斩。**
> 本文原先写「`parent-agent` 是默认注入集三个来源之一，而它的供给被砍掉
> 一半」，依据是「assistant/message 事件被丢弃 52.6%」。这是把**事件条数**
> 当成了**供给量**。实测 `session-43422ed9`：被丢弃的 381 条 assistant 事件
> **携带的文本字符数合计为 0**——它们之所以被丢弃，正是因为 `textOf` 从中
> 取不到任何 `type==='text'` 块。有文本的 341 条全部入库，共 72431 字符。
>
> 换句话说，丢弃率 52.6% 是**按条数**算的，而按**内容**算是 **0%**：
> `parent-agent` 一个字符都没少。这个错误值得留在这里，因为它的形状与
> 教训 2 同型——**一个比率的分子分母必须量同一件东西**，而「事件条数」
> 与「进入 extract 的材料」不是同一件东西。真正缺的从来不是 assistant
> 文本，而是 `tool/call`：那才是 100% 丢弃、且丢的是**全部内容**。
>
> 这一更正直接决定了修法：M1 因此**否决**了「让无文本块的 assistant 消息
> 也不丢弃」——采集它换不来任何 `parent-agent` 供给，见下文 M1。

## 业界对照

### TencentDB-Agent-Memory —— 差异恰好就在我们丢弃的那一行

[`MemoryCore/scripts/import-opik-to-memory-skill-py/import_opik.py:352-358`](https://github.com/TencentCloud/TencentDB-Agent-Memory/tree/feat/server_team)：

```python
text = content_to_text(raw.get("content") or raw.get("text"))
if text and text.strip():
    out.append({"role": mapped, "content": truncate(text)})
if mapped == "assistant":
    out.extend(extract_tool_calls(raw))    # ← 我们缺的正是这一行
```

**先取文本；文本为空不影响 `tool_call` 的独立采集。** 我们只做了第一步。

三条可借鉴的判断：

| 判断 | 腾讯 | 我们 |
|---|---|---|
| tool_call 是独立 role | `{"role":"tool_call","content":<args>,"tool_call_id":cid,"tool_name":name}` | `tool/call` 被 `continue` 丢弃 |
| 强制截断 | `MAX_MSG_CHARS = 32_000`，超出加 `…[truncated]` | 采集侧**无上限**（仅 extract 侧有 6000） |
| 孤儿清理 | `drop_orphan_tool_results()`：无配对请求的结果一律丢弃 | 无此概念，且**全部结果都是孤儿** |

第三条尤其刺眼：腾讯把「结果必须有对应的请求」当作不变量，而我们全库只有
结果没有请求——按它的规则，我们 L0 里每一行工具结果都会被判为孤儿。

记忆是**显式工具写入**（`memory_tool.py` 的 add/replace/remove），没有自动
转写层，`handle_tool_call` 只做分发。它靠 `memory_char_limit` /
`user_char_limit` 在**写入时**拒绝超限（该判断已在 ADR 0007 借鉴）。
**它不做 L0，对本议题无参考价值。**

### memorax-code —— 不可比

检索与预算在闭源服务端，本地仅采集适配与 HTTP 客户端；全仓 grep
`budget|token_limit|char_limit` 零命中。

## 修复实施（M1–M8，已落地）

方案经审查后定为八项。**其中两项是「不做」**，且不做的理由与做的理由等重——
它们被写进本文，正是为了不被下一个人重新提出来。

### M1 · 只采 `tool/call` 事件，不采 assistant 的 tool_use 块（**否决**）

原修复方向的第 2 条（「assistant 消息即使无文本块也不整条丢弃」）**已否决**，
两条独立理由：

1. **它换不来任何东西**。见「更正二」：被丢弃的 assistant 事件携带 0 个文本
   字符，采集它们只会得到一批空行。
2. **它是同一事实的第二处实现**。实测本机全部 143 个 session 日志，13715 对
   `assistant.tool_use` 与 `tool/call` 事件的 `arguments` **逐字节全等**
   （mismatch 0，orphan 0）。而 tool_use 块是两者中较弱的一份：它没有自己的
   `callId` 配对关系，也没有独立于事件的 provenance 来源。

`classify` 的 `assistant/message` 分支因此**保持原样**，一行未改。

### M2 · `arguments` 必须结构化摘要（禁止 raw，禁止 head400）

保留短值原样、长值记为长度占位：

```
{"query":"工程取舍","kind":"fact"}                  → 原样
{"content":"<4821 chars>","file_path":"src/a.ts"}   → 长值省略为 <N chars>
```

**raw 与 head400 都是负收益**，这与直觉相反，所以实测数据必须留档。按
extract 实际装进预算的事件总数：

```
current(不采)  504
raw            458   ← 净减 9%
head400        458   ← 净减 9%
elide120       563   ← 唯一为正，净增 12%
```

根因是**长 `arguments` 的长度集中在单个值上**——一个文件正文、一段 heredoc、
一整份文档。从头截 400 字符，恰好留下最没有信息量的那 400 个字符，并把它后面
的字段名全部切掉：这条记录于是变成「write_file，以及正文的前 400 字」，
连写的是哪个路径都不说，却照样占满一整行预算。

`<N chars>` 是**测量**而非省略号：「这里有过一段 4821 字符的载荷」是模型可以
据以推理的事实，而「…」只是邀请它猜。

### M3 · 两级上限，且是执行断言而非注释声明

- **值上限 `TOOL_CALL_VALUE_CHARS = 120`**：这是**重尾分布上的成本权衡**，
  不是分布形状的特征。实测 13961 次调用的 35829 个值，**等宽**分桶后密度
  单调下降（11840 → 6686 → 4033 → 2254 → 1029 → 778，六桶跌约 20 倍），
  **没有第二个峰**：

  ```
  cap    保留原样的值    保留原样的总字节
   80        69.3%           628048
  120        74.4%           807266
  160        78.5%          1009564
  200        81.2%          1185859
  ```

  120 → 200 多得 6.8 个百分点的覆盖，要多花 **47%** 的原样字节，而这些字节
  花在 `EXTRACT_EVENT_EXCERPT_CHARS` 之内，挤掉的是同一次调用的其他字段。
  120 是这条成本曲线的拐点。

  > **初稿此处写错**：称该分布「双峰」、120「落在波谷」。那是**不等宽分桶
  > 的错觉**（20 宽的 `[100,120)` 与 40 宽的 `[120,160)` 并排印在一起）。
  > 等宽重算后唯一的回升是 `[120,140)` 的 +3.0%，属噪声——同一次扫描在更远处
  > 有十五处同量级或更大的回升（`[500,520)` +96%、`[660,680)` +22%）。
  > **取值没变，理由必须换**：把它说成波谷，是让结论强过证据，而这个数从此
  > 就靠一个并不存在的形状支撑着。

- **行上限 = `EXTRACT_EVENT_EXCERPT_CHARS`（400）**，这是**不变量**而非第二个
  常数：extract 把每条事件都切到 400，所以采集侧多存的字节**永远不会被读到**。
  一个数，两个执行点（沿用 `worstPersonaTokens` 的先例）。

两级缺一不可，且被两条独立的测试分别钉住：只做值省略，一次带 30 个短字段的
调用照样写出超长行（实测 13721 次里有 2 次）；只做行上限，长值就会原样进来。

**另有一处必须是 try 而非断言：摘要构造整体不得抛异常。** `JSON.parse` 不是
唯一会抛的成员——`JSON.stringify` 递归，深嵌套值会 `RangeError`（实测本机
约 4500 层为界：**`parse` 成功，`stringify` 在返回途中溢出**）。初版的 `try`
只包住 `parse`，**保护了错误的那一半**。后果不是丢一行：`collectTurnEvents`
构造的是**整个 turn**，所以一次这样的调用会把该 turn 的 L0 全部带走，
**包括用户自己的消息**，而 `auto-extract.ts` 的 fail-open catch 会把它变成
一行 warn——静默失效。

真实语料最大嵌套深度为 **5**（13961 次调用），今天不可达；但 `arguments`
按本模块自己的定义就是「模型原样产出、可被 prompt injection 操纵」的字符串，
而 `transcript.ts` 正是 fail-closed 的注入安全边界。**「目前没有输入能做到」
是运行时事实，不是不变量**——这正是本文件对每个数字反复要求的那种区分。
降级走**既有的** `bound(elide(raw))` 路径，不新增第二条恢复路线。

**同一根因的第二处，由 QA 发现：`name` 非字符串同样带走整个 turn。** 修复
`arguments` 时，同一行上的 `name` 被漏掉了：

```ts
label: toolLabel(TOOL_CALL_PREFIX, event.data.name),   // ← 无收窄，直接进 .replace
text:  summarizeArguments(String(event.data.arguments)) // ← 有
```

`undefined`/`null`/数字/对象/数组五种输入全部抛出（`value.replace is not a
function`），后果与深嵌套完全一致：**整个 turn 的 L0 丢失**。而且这是**本次
改动新引入的**——修复前 `name` 只进 `callNames` Map，`Map.set` 接受任何值。

修在 `toolLabel` 内部**一处**（把参数类型改为 `unknown` 并收窄），不是在两个
调用点各写一次。这个选择当场被验证是对的：`tool/result` 分支看起来有
`?? ''` 兜底，**但它只覆盖 nullish**，数字类型的 name 照样穿过去抛在同一个
地方——**一条规则写两遍，其中一遍已经是坏的**。

顺带修正 `arguments` 的 `String()`：`String(undefined)` 会把字面文本
`"undefined"` 写进 L0，那是**捏造的事实**。两个字段现在都用同一种收窄。

> **可达性诚实说明**：QA 扫描 145 个 session、14077 次 `tool/call`，`name`
> 与 `arguments` **100% 是 string，今天不可达**。仍然修，理由与深嵌套那条
> 逐字相同——而且工具名来自第三方插件/MCP server 注册，本模块自己的注释
> 就写着它「与 sender id 一样不可信」。

### M4 · 独立 label 前缀，复用既有清洗

`tool/call` 用 `tool-call:<name>`，与结果的 `tool:<name>` **分属两族**。
理由不是洁癖：`metrics.ts` 与 `scripts/inspect.mjs` 把结果族当作一个**总体**
在统计——

```sql
count(label='tool:memory_recall' AND text LIKE 'No stored memories matched.%')
/ count(label='tool:memory_recall')
```

——请求若混入同一 label，**分母翻倍而分子不动**，未命中率直接腰斩，而这正是
阶段 4 的门禁数（ADR 0005）。指标会继续返回一个数，那个数是错的，且锁「措辞」
的测试照样全绿——与「纠正三」完全同型的失效。审查核实 5 处消费者全部使用
**精确相等**匹配，故独立前缀对它们不可见，无需改动任何消费者。

前缀是 `toolLabel` 的**参数**，不是第二处字符串拼接：请求与结果遵守同一条规则
（同字符集、同长度上限、同降级），差别只在归属哪一族。写第二个 `` `tool-call:${…}` ``
就是 D7–D9 的缩影——而这个 bug 在本文件**已经发生过一次**（`tool:` 分支当初
被写成没有 strip 的版本）。

### M5 · provenance 固定 `tool-output`

按 §2.4 fail-closed，**绝不给 `parent-agent`**。`tool/call.data.arguments` 按平台
定义是「模型原样产出、未经解析的字符串」，前序 tool 输出里的 prompt injection
可以操纵它；而 `parent-agent` 是 §2.3 **默认注入集**三来源之一。给它就是为
「模型可控文本 → 每轮注入包」开一条新通路——这正是 `transcript.ts` 存在的那条
边界。请求被如实记录为「有人要求了什么」，信任度取「所有可能塑造过它的东西里
最低的那个」。

### M6 · 把 extract 输入纳入 `worstExchangeChars`，并由它解出 5300

**这是一个真实的守卫覆盖漏洞，不只是一个数字问题。** `worstExchangeChars`
原先只给 rollup 定价，于是 `EXTRACT_TRANSCRIPT_CHARS` **可以被改成任意值而
不会有任何断言失败**——唯一提到 extract 的断言只给它的**回复**定价。

补上后，不变量是：

```
EXTRACT_TRANSCRIPT_CHARS + worstExtractReplyChars() ≤ LLM_MAX_TOKENS
5300 + 6682 = 11982 ≤ 12000
```

**回复项是「构造出来再量」的，不是估的。** 这条原则本身没变，变的是
「构造」里还藏着多少没被检验的假设——**这个数被下调了三次，每次都是因为
真的去量了一遍**：

```
脚手架「每候选 +60」、seq 4 位        上限 7100   （估的）
构造计价；引号类转义、seq 4 位        上限 6558   （量的）
+ seq 6 位、控制字符类转义            上限 5318   （量的）
```

- **第一轮**把脚手架写成「每候选约 60 字符」，取值 7000，并留下一句自白：
  *「那是估计值不是实测上界」*。风险写在纸上，假设从未被测。
- **第二轮**把候选构造出来交给 `JSON.stringify`，得每候选 165，
  **7000 超出真实上限 442**。
- **第三轮**发现**构造本身**还带着两个未检验假设：

  | 假设 | 原值 | 实测 |
  |---|---|---|
  | seq 宽度 | 9999，注释称「4 位是现实 transcript 最宽的」 | 真实 L0 3312 行中 **74.8% 已超 4 位**，最大 **126635**；145 个平台日志中 30 个超过 9999 |
  | 转义**价格** | 按 `"` 计 +1 | `\u001f` 类控制字符计 **+5**，而 title/body 是模型自由文本 |

  第二项是主项：同样 6% 的**计数**率，仅把价格改成最坏类别就把上限从
  6602 压到 5462；seq 宽度约 140，第 10 个 `sourceSeq` 约 140。

**取值 5300**（上限 5318）。相对「按实测现实计价」（0.44% 转义、全是引号类、
6 个 seq → 上限 6867），这个常数背负了约 **1550 字符的刻意悲观**——方向是
对的：守卫保护的是 provider 的硬上限，在那里估错的代价是回复被截断、
job 进死信。

**代价必须写清楚：5300 低于原始的 6000**，转写预算确实比改动前更小了。
但整体仍是净赚，因为 `skip` 与工具调用行补得回来（48 个真实 session）：

```
baseline 6000 + break + 不采      kept 2704  (asst 837, res 1636)
本次      5300 + skip  + 采        kept 3021  (asst 635, call 1133)
```

**事件总数 +11.7%**，外加 1133 条此前在 L0 中根本不存在的工具调用——代价是
assistant 行少 24%。**一个会让预算变小的诚实上界，仍然优于一个会让 provider
截断回复的宽松上界。**

6000 的来源已由 `git log -S` 查明：初始提交 `37c73f5` 直接写死，此后从未修改，
也从未论证——**那是它唯一的合法来源**，现在被一个能算出来的数取代。三次下调
说明的正是这件事：**估出来的数只会偏向对自己有利的一侧。**

顺带记录一个必然结果：最坏交换现在是 extract 的（5300+6682=11982），不再是
rollup 的（6000+4260=10260）。两侧都按**每字符一 token** 的 CJK 悲观价计价。
断言取各 prompt 的 max，所以它始终指向当前最坏的那个，无需被告知是哪个。

### M7 · `renderTranscript` 的 `break` → `skip`

`extract` 是全仓**最后一个**还在用 `break` 的预算点。`recall/render.ts` 的
`withinBudget` 早已把同一问题定成 skip，注释里写得很直白：「An entry that does
not fit is SKIPPED, not treated as end-of-list」。原来的 `break` 让**一条超长
记录变成一堵墙**——它后面的东西无论多便宜都看不见了。实测 +4%。

**没有**直接复用 `withinBudget`，且这不是待清理的欠账：它按 `renderEntry` 给
**token** 定价（容器是注入包），extract 按 JSON 条目给**字符**定价（容器是
prompt 载荷）。两个容器、两把尺、一条规则——正是 `constants.ts` 在「载入期
派生守卫」与「运行期个人上限」之间划的那条线。硬共用函数，就等于用另一个容器
的尺子量这个容器。

### M8 · `renderTranscript` 的选择策略保持「按 seq 顺序」（**否决 trust-first**）

trust-first（先装高信任材料）看起来最诱人：它让「高信任材料占比」这个指标
大幅上升。**否决**，两条理由：

**1. 它砍掉的正是模型真正在用的东西。**

判据不是「装进去的是什么」，而是**模型实际引用了什么**——后者可以直接测：
`extract.ts` 把每条候选的 `sourceSeqs` 按 `[label] text` 写进
`evidence.excerpt`，所以那张表逐段记录了模型引用过哪个 label 族。实测
8 个真实库、167 条带 session 证据的记忆、295 个被引段：

```
按段计       tool-result 55.9%   assistant 37.3%   user 6.1%
按首段计     tool-result 59.3%   assistant 28.7%   user 10.8%
按「引用过该族的记忆」计    tool-result 82.0%
各库分别（按段）：52% / 57% / 59% / 65%
```

**工具结果是模型引用最多的一类材料**，四个库无一例外。

再把这些**被实际引用过的行**放回预算重放，看两种排序各留下多少：

```
                      总留存    工具结果留存
seq 顺序（现状）        93%         90%
trust-first             81%         66%
```

trust-first 不是「提纯」，是把模型实际引用过的工具结果**删掉约四分之一**。
它优化的是一个中间指标，代价是最终产物。

> 口径说明：上表在最终值 `EXTRACT_TRANSCRIPT_CHARS=5300` 下测得。换成
> 6000 是 96%/94% 对 86%/75%，6500 是 97%/96% 对 89%/81%，7000 是
> 97%/96% 对 90%/83%。**结论不随口径变化**：四个取值下 seq 顺序都明显占优，
> 且预算越紧、trust-first 的损失越大（这符合直觉——预算越紧，排序越决定结果）。

**2. 它把 §2.4 的「安全」分级挪用为「信息价值」分级**——两个概念的混用。
provenance 回答的是「这段文本能不能进默认注入包」，不回答「这段文本值不值得
读」。一条 `tool-output` 的 bash 报错可能是整轮里最有价值的事实；它信任度低
不代表信息量低。让排序读 provenance，等于让一张安全表去干信息检索的活。

**按 seq 顺序是唯一不做价值判断的规则**，因此保留。

> **本节曾用错数字，登记为同型错误第三例。** 初稿写「trust-first 把高信任
> 材料从 43% 提到 91%，把工具结果从 32% 砍到 5%」。这四个数**复现不出来**：
> 43%/32% 在 BASELINE 上任何口径都算不出；而 91% 与 5% **来自互不相容的两个
> 分母**——5% 只在「L0 原始字节」这个分母下出现，**正是本文「更正三」自己
> 批判过的那个错误**。已全部删除，换成上面可复现的直接判据。
> 这是本文一轮之内第三次「分子分母量了不同的东西」（更正二、更正三、本条），
> 也是**第三次恰好把结论说得比证据强**。

### 采集侧强制截断（原方向第 3 条，已落实）

由 M2+M3 实现。本项目已被「无界」坑过三次（rollup 输入、注入回退分支、
本文第 4 项），采集侧没有成为第四次。

## 真实数据验收

在本机全部真实 session 日志上重放（只读），对照修复前后的构建产物。
strataloom 工作区 48 个 session：

```
配置                              kept  asst  call   res   高信任%  结果%
BASELINE seq+break 6000 不采      2704   837     0  1636    36%     61%
P3       seq+SKIP  5300 elide120  3021   635  1133  1036    25%     34%

  kept +11.7% | asst −24.1% | res −36.7% | 工具调用 0 → 1133
  L0 字节 8723819 → 9445094 (+8.3%)
  孤儿率  5699/5699 = 100.0%  →  68/5699 = 1.2%
```

> 口径：session 数会随本机新会话增长（本轮先后测得 47/48），重放脚本
> 枚举 `~/.dsh/sessions/<workspace>/*/session.jsonl.zstd` 且要求至少一个
> `turn/start`，不做其他筛选；`strataloom` 口径为工作区名含 `strataloom`。

**代价随每轮复核而变大，如实记录这条轨迹**——它本身就是结论的一部分：

```
                              转写上限   kept    asst     res
初稿（脚手架估 60）             7000    +43.5%   −5.5%  −15.4%
构造计价后                      6500    +34.6%  −10.9%  −20.9%
+ seq 6 位、控制字符转义        5300    +11.7%  −24.1%  −36.7%
```

**每一次「把数算对」，代价都变大，收益都变小。** 这正是估算的危险之处：
它不是随机偏差，而是**系统性地偏向对自己有利的一侧**。但 1133 条此前完全
不存在的工具调用、以及孤儿率从 100% 到 1.2%，在最保守的口径下依然成立。

**残留的 1.2% 孤儿有确定成因，不是配对逻辑的缺陷**：它们来自零参数工具
（`list_agents`/`get_goal`/`job_list`）——平台对这些调用记录的 `arguments`
是**空字符串**（实测 117 次全部如此），摘要后文本为空，被 `collectTurnEvents`
**既有的**「文本为空则丢弃」过滤掉。这条过滤先于本次修复存在，且丢弃的确实是
零内容的行。另有少量 `tool:unknown`，是跨 turn 的 `callId` 无法在本 turn 内
解析所致，同样是既有行为。两者都不在本次修复范围内，登记于此以免下一个人把
1.2% 当成 bug 去查。

**「高信任%」下降不是退步，分母变了。** 修复前 kept 里只有 assistant 与工具
结果两类在竞争，修复后多出 1133 条按 §2.4 必然是 `tool-output` 的请求行
（M5）。把这个比率当成质量指标，正是 M8 否决 trust-first 时指出的同一种混用
——事实上 M8 初稿引用的 43%/91% 就是这个陷阱的实例。

### 第三个消费者：`sourceOf` 的读出口（行预算，不会自适应）

**这一条差点漏掉，漏掉的原因值得记下来。** L0 有多个消费者，而它们用的
**不是同一把尺**：

- `extract` 按**字符**计预算（`EXTRACT_TRANSCRIPT_CHARS`），行密度一变它
  自己就重新平衡了，代价被逐条量到了百分点；
- `sourceOf`（`readSessionTurns`）按**行数**计预算（`SOURCE_TURN_LIMIT`），
  行密度上升 67.7% 后，同样 20 行买到的真实对话直接少了三分之一，
  **而且它不会报告任何异常**。

实测 140 个真实 session，在 `SOURCE_TURN_LIMIT` 保持 20 的情况下：

```
L0 行/session      148.6 → 249.1  (+67.7%)
窗口文本字符    3632503 → 2373356  (−34.7%)
窗口内 assistant 行  548 → 358     (−34.7%)
```

`sourceOf` 正是**核对原话**那条路径——让 provenance 可核查而非仅仅被声称。
损失恰好落在证据本该在的地方。

**修法：`SOURCE_TURN_LIMIT` 20 → 34，且该数由密度算出**：

```
20 × (249.1 / 148.6) = 20 × 1.677 = 33.5  →  向上取整 34
```

重放独立验证：盈亏平衡点落在 32（−2.3%）与 33（+0.3%）之间，34 相对旧窗口
为 +3.4% 字符 / +3.6% assistant 行。**推导与实测两条路给出同一个数，相差
不到一行。**

**否决的替代方案**：把 `tool-call:` 族从该查询里排除，可以保持 20 行不变且
零成本。但请求行占窗口 39.7% 恰恰因为**它们就是「agent 做了什么」**——
查证一条记忆的来源时，看到调用与看到结果同样必要。在读出口把它们滤掉，
等于在另一端重新制造这次改动本身要消除的那种盲区。

**一般教训**：改动 L0 存什么，必须对照**每一个消费者各自的尺子**重新核算；
按行计预算的那个**没有自我修正能力**。

### 更正三：「3–7%」那个数字错在分母

本轮调研中曾出现「extract 只读到 L0 的 3–7%」这一说法，用以论证输入残缺的
严重程度。**该数字的分母是错的**，实测：

```
L0 原始文本字节            8026816
候选集合 (Σ min(len,400))  1818359   ← 400 字符以上的内容根本不在候选里
extract 实际读到的字节      610081

错误分母（L0 原始）:  7.6%
正确分母（候选集合）: 33.6%   （按行数：2621/7956 = 32.9%）
```

分母用 L0 原始字节，等于把「每条事件超过 400 字符的那部分」算进「本应被读到
却没被读到」的份额——但那部分**从设计上就不在候选集合里**，它被
`EXTRACT_EVENT_EXCERPT_CHARS` 排除，与预算是否装得下无关。

**「装不下」≠「我们主动不看」。** 前者是预算问题，可以靠调 M6、M7 改善；
后者是逐条截断策略，是另一个决定。把两者塞进同一个比率，会让预算问题看起来
比实际严重四倍，并诱导出「把 `EXTRACT_TRANSCRIPT_CHARS` 大幅调高」这类
针对错误根因的修法。与「更正二」同型：**分子分母必须量同一件东西。**

> **第三例紧随其后**：M8 初稿引用的「43%/32% → 91%/5%」里，那个 5% 用的
> 正是这里刚被判为错误的「L0 原始字节」分母，而 91% 用的是另一个分母——
> 同一句话里的两个数来自两把尺。详见 M8 节末的登记。一轮之内三次同型错误，
> 说明这不是笔误而是**默认习惯**：拿到两个数就相除，不先问它们量的是不是
> 同一件东西。

## 教训

1. **「数据不存在」与「我没去查那个地方」是两回事。** 我查了插件的 8 个库
   就断言证据从未被采集，而它就在插件每轮都要读的 `session.events` 里。
   下结论前先问：**我查的范围，是不是就是数据应该在的范围？**
2. **门禁判据失效时，先查判据的每一半是否还成立。** 我接受了「比率显著」
   这一半，只去补另一半——而前一半的样本 99% 已被自己的 v9 修复作废。
3. **把不可信输入放到指标的判定位上，是一种沉默的失效。** 合并方案会让
   `RECALL_NO_MATCH` 的前缀被模型控制，而锁常量措辞的测试照样全绿。
   这是「测试全绿 ≠ 产品有效」的第五次实例。
4. **调研要读源码，不读 README。** 三个项目里只有一个真正可比，另两个的
   核心逻辑或在服务端、或根本没有对应层——如果只看文档描述，会误以为
   三个都能借鉴。
5. **一个比率的分子与分母必须量同一件东西。** 本文一轮之内犯了**三次**：
   「`parent-agent` 供给腰斩」用事件**条数**冒充**内容量**（更正二）；
   「extract 只读到 3–7%」把设计上就不在候选集合里的内容算进分母（更正三）；
   M8 初稿的「91% 对 5%」两个数来自两个互不相容的分母，其中 5% 用的正是
   更正三刚判过的那个错误分母。三次都不是算错，是**量错了对象**——
   而三次都恰好把结论说得比证据强。三次同型说明这不是笔误而是默认习惯：
   **拿到两个数就相除，不先问它们量的是不是同一件东西。**
6. **符合直觉的修法要先测，尤其是「多存一点总没坏处」。** raw 与 head400
   都是「把参数存下来」的自然写法，实测都让 extract 的输入**净减 9%**——
   因为一条昂贵而低信息量的记录会挤掉多条便宜而有信息量的记录。预算是零和的，
   所以「采集什么」和「采集多少」是同一个决定的两面。
7. **把风险写进注释，不等于处理了风险。** 本轮两处同型：`EXTRACT_TRANSCRIPT_CHARS`
   的初版注释明写「60 是估计值不是实测上界」，然后照样按它解出上限、只留 100
   余量——实测脚手架是 165，取值超出真实上限 442；`summarizeArguments` 的
   文档明写「must never throw on the capture path」，而 `try` 只包住
   `JSON.parse`，`JSON.stringify` 在保护之外。**一句自陈的免责在下一个读者
   眼里会读成「已经考虑过了」**，于是没有人再去测。正确做法只有两个：
   把它量出来（M6 现在构造最坏候选交给 `JSON.stringify` 计价），或者把它
   执行出来（M3 的行上限、item 1 的整体 try）——**断言与构造，都不是注释。**
8. **估出来的数会系统性地偏向对自己有利的一侧。** `EXTRACT_TRANSCRIPT_CHARS`
   在本轮被下调了**三次**（7100 → 6558 → 5318 上限），每一次都是因为真的去量了
   某个此前只是「看起来合理」的假设：脚手架 60、seq 四位、转义按引号计价。
   **三次全部同向**——没有一次是量完发现比原估计更宽松的。相应地，验收数字
   一路从 +43.5%/−5.5% 走到 +11.7%/−24.1%。收益仍然成立，但**如果只做前两轮
   就交付，报告里的代价会比真实代价小一半**。
9. **改动一层的存储，必须对照每个消费者各自的尺子重新核算。** `tool/call`
   采集让 L0 行密度涨了 67.7%。按**字符**计预算的 `extract` 自动重新平衡，
   代价被逐条量到百分点；按**行数**计预算的 `sourceOf` 则把整个密度变化
   吞成了内容损失（−34.7%）**且不报告任何异常**，差点无人登记。
   **不会自适应的那个预算，恰恰是最不会喊疼的那个。**
10. **同一根因要在所有同型位置一次修完，并优先修在共用函数里。** 深嵌套
   `arguments` 与非字符串 `name` 是同一个「采集路径抛异常 → 整个 turn 丢失」，
   相隔一行，第一轮只修了其中一个。修 `name` 时选择改 `toolLabel` 内部而非
   两个调用点，当场就被验证是对的：`tool/result` 的 `?? ''` 看着像兜底，
   **实际只挡 nullish**，数字类型照样穿过去——**一条规则写两遍，其中一遍
   已经是坏的。**
