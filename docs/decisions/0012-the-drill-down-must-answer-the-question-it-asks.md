## 一、事实：承诺「核对原话」，实现取的是会话末尾

ADR 0009 已登记 `SOURCE_TURN_LIMIT` 是惰性常量，并明写「**不修实现就必须改
承诺**」。本轮补上了 ADR 0009 **从未测过的那一层**。

此前三次测量问的都是「**投递了几行**」，没有一次问「**投递的内容里有没有
被引的那句话**」。补测方法：对每条带 `evidence.excerpt` 的记忆，把 excerpt
拆成被引段、剥掉 `[label]` 前缀与尾部省略号，取每段前 60 字符作探针，去
「当前 `sourceOf` 实际投递给模型的文本」里找。

```
label        segs  found-in-DELIVERED  found-in-WHOLE-L0(对照组)
tool          349     18 (5.2%)        349 (100.0%)
assistant     164     18 (11.0%)       164 (100.0%)
tool-call     125     10 (8.0%)        125 (100.0%)
user           24      0 (0.0%)         24 (100.0%)
context         5      0 (0.0%)          5 (100.0%)
subagent:*      5      0 (0.0%)          5 (100.0%)
TOTAL         672     46 (6.8%)        672 (100.0%)
```

**对照列是决定性的**：同样的探针在「整个会话的 L0 全文」里 100% 命中。
所以 6.8% 不是探针匹配不上的假象，而是**内容确实在库里、确实没被投递**。

三方独立复算，三种方法、三个分母，同量级：

| 测量者 | 方法 | 分母 | 被引段抵达率 |
|---|---|---|---|
| 审计（本文） | 子串探针 | 672 段 | **6.8%** |
| 方案评审 | 构造式反演（按写者渲染规则重建） | 769 段 | **6.1%** |
| QA | 按段独立计数 | 778 段 | **1.5%** |

**投递的绝对数三方一致（46）**，分母口径不同。按记忆聚合：
**88–96% 的记忆一个被引的字都看不到**。

### 根因是两级损失，不是一级

`readSessionTurns` 取 `ORDER BY seq DESC LIMIT 34`（会话**最末** 34 行），而
被引的话在会话里均匀分布——实测相对位置 **p25=0.24 / p50=0.57 / p75=0.80**：

```
落在末尾 34 行窗口内           : 70/754 = 9.3%    ← 第一级：SQL 就丢掉 90.7%
窗口内再被 token 预算投递出去  : 46/70  = 65.7%   ← 第二级：再丢 34.3%
```

**所以把 `SOURCE_TURN_LIMIT` 调到无穷也解决不了**（实测 limit=5000 只到
8.5%）：必须换**选择规则**，不是换**窗口大小**。ADR 0009 §六(a) 否决调大该
常量的结论因此更强——它当时的理由是「收益极小」，真正的理由是**锚点就是错的**。

### 一个更能说明问题的数字（QA 独立发现）

BEFORE 下 **322 条记忆只对应 13 个不同的 packet**，最大一组 **98 条记忆**
返回**逐字节相同**的 7.4KB 会话尾巴。即旧 `sourceOf` 在语义上**根本不是一个
按记忆区分的函数**——它承诺「这条记忆的出处」，实际返回「这个会话的结尾」。

## 二、修法：去读那个已经写好的答案

正确答案**已经存在于库里**。`evidence.excerpt` 存的正是提炼时实际引用的那几段
原文——`plugin-architecture.md` 第 970 行：「`evidence.excerpt` 存**真实引文**
而非来源 seq 列表——D3 要求可审计，一串序号对审计者不构成证据」。

所以修法不是调预算、不是加机制、不是加列，而是**让这条读路径去读那个答案**：

- `service.source()` 单查询多取 `e.excerpt` 与 `m.provenance`；
- excerpt 非 NULL ⇒ 返回**一个** `TranscriptEvent`，body 是 excerpt **逐字节原文**；
- excerpt 为 NULL ⇒ 回退到 `readSessionTurns`，行为逐字节不变（实测 79/79 相同）。

**零 schema 变更、零渲染器改动、净删一条规则。**

### 2.1 不解析 excerpt——这是本轮最重要的一条禁令

方案初稿要按 `\n---\n` 把 excerpt 拆成段落分别返回。**方案评审否决了它**，
依据是 `extract.ts` 366–389 行**明文写下的告诫**：

> KNOWN LIMIT, stated rather than papered over: `\n---\n` is a separator an
> event's own text can WRITE… it is **NOT a machine-parseable format and no
> consumer should treat it as one**.

实测代价：**778 段里有 25 段（3.21%）**因分隔符歧义丢失 `[label]` 前缀，
**无法归属来源**——审计者看到一段文字，无法知道是用户说的还是 bash 输出的。
**在一个为兑现 D3 的修复里，引入这段注释预先警告过的 D3 违反。**

> **评审给出的替代方案是加 schema（`evidence` 加一列承载 `sourceSeqs`），
> 而不是不拆。** 主 agent 实测后选了第三条路：**根本不解析**——excerpt 整体
> 逐字节返回为单个 hit。实测结果决定了它：
>
> ```
> 322/322 = 100.0% 整段投递    渲染成本 p50=112 / p90=205 / max=471 tok（预算 1820）
> 最大渲染包 2086 字符（容器 8192）
> ```
>
> 不解析**不但避开了歧义，投递率反而是 100%，且零 schema 变更**。
> 「能不能不解析」的答案是「能」，所以就不解析——**这是「少就是多」在本轮
> 唯一一次以「三个方案里选最少的那个」的形式出现**。

### 2.2 两条路径必须自我标注

ADR 0009 §五第 3 条的明文要求。**回退不是边缘情况**：实测 **79/401（19.7%）**
的证据行 excerpt 为 NULL（**全部**是 `principal-explicit`），近五分之一的读取
走回退。混成同一批无差别 hits，审计者**在最常见的情形下**分不清看到的是
证据还是上下文。

标注走**已有字段**（`transcript.ts` 的 `QUOTE_LABEL='quote'` / `QUOTE_SEQ=-1`），
经 `tools.ts` 既有映射渲染为 `kind` / `id`：

```
引文： - [quote] (id seq -1) tool-output: [user] 这个仓库统一用 pnpm…
回退： - [user]  (id seq 2)  human:       这个仓库统一用 pnpm…
```

**不碰撞论证经三方独立核验**：`classify` 是 L0 标签的唯一生产者，值域为
`user`/`assistant`/`context`/`subagent[:id]`/`tool:<name>`/`tool-call:<name>`
——每个动态形式都带前缀和 `:`，故捕获行**永远不可能**是裸 `quote`（名为
`quote` 的工具只得到 `tool:quote`）。`seq` 恒非负，故 `-1` 不可碰撞。
常量放在 `transcript.ts` 而非别处，**因为使它安全的正是 `classify`**。

> **边界要说清**（QA 实测）：该保证的作用域是「**经 `classify` 写入的行**」。
> `conversations.label` 无 `CHECK` 约束，绕过 `classify` 直写 DB 可同时伪造
> `quote` 标签与 `human` 信任级。这**需要本地文件写权限**，而有该权限者本就
> 能改任意记忆，**非本轮引入的提权**——但本轮**提高了 `label` 字段的价值**
> （它现在承载「这是引文」这一审计断言），而该字段仍无 schema 级约束。
> 已登记为待办（§六）。

### 2.3 删除 `EXCERPT_COMPACT_MS`，而不是调大它

excerpt 一旦成为主证据源，`decay.ts` 那条 30 天 compaction 就从「清理没人读
的列」变成「**销毁 D3 的证据**」。

**初稿的理由是错的，且被评审推翻——这一条值得记，因为结论没变而理由全换。**

- ❌ 初稿：「它比 L0 的 90 天**早死 60 天**」。
- ✅ 真相：`pruneConversations` 的豁免子句使**被存活记忆引用的 L0 永不删除**
  （实测 **6273/6321 = 99.2%** 的 L0 行受该豁免保护）。所以差值**不是 60 天，
  是无穷**——**证据会死，而它所引的原话永远不死**。

不变量应表述为「**证据不得先于它所支撑的记忆或原话消失**」。

**为什么删除而不是调大到 90 天**：
1. 「证据活多久」这个事实**已由 `pruneConversations` 的豁免子句定义**，再写
   一条独立的 30 天规则就是 D7–D9 的又一实例；
2. 对一个**无上界**的寿命而言，**任何有限窗口不是数据丢失 bug，就是永不
   触发的死代码**；
3. 体积论据成立且口径已订正：excerpt 是 L0 **字符**的 **3.216%**、**字节**的
   **3.258%**（初稿把字符数标成了字节，见教训 3）。

**紧迫性是实测的，不是修辞**：该规则当前清 **0 行**，但带 excerpt 的最老记忆
`updated_at = 2026-08-23T15:29:03.655Z`，即 **2026-09-22 起开始咬**，其后 30 天
内清空 **322/322 = 100%**。QA 用对照组实地验证了这一点：**旧版 decay 一次跑
清空 55/60 条 excerpt，新版清 0 条**。

> **所以两项改动不可拆。** 若只发读路径修复而不删这条规则，**修好的证据会
> 在三周后被逐条抹掉，而全部测试仍然全绿**。

## 三、修复引入的新缺陷，以及它为什么比原缺陷更坏

**代码审查与 QA 两个独立 agent 各自复现了同一个必修缺陷**，主 agent 亦亲手
复现。这是本轮流程最有价值的一次拦截。

`renderEntry` 把 body 的每个 `\n` 缩进成 `\n␣␣`，**渲染字符最坏膨胀近 2 倍**。
于是一条**写者值域内合法**的 excerpt：

```
存储字符   : 4165        ← 写入侧界内（WORST_SOURCE_SEQS=10 × EXTRACT_EVENT_EXCERPT_CHARS=400）
渲染字符   : 8236        ← \n → \n␣␣
估价       : 2059 tok    vs RECALL_PACKET_BUDGET_TOKENS = 1820
withinBudget 保留 : 0    ← 唯一的 hit 被整条 continue 跳过
renderFramed 输出 : ''
模型看到   : "No stored memories matched."
```

**记忆存在、证据存在、`source()` 也返回了它，而模型被告知「没有匹配的记忆」。**

**它比原缺陷更坏**：原缺陷给出**错的上下文**，新缺陷给出**主动误导的否定**，
并且**掩盖了记忆本身的存在**。它恰好否定本轮改动的核心主张。

**根因是两个界的单位不同**：写者按**存储字符**设界，读者按**渲染后 token**
计价。「4165 < 7280 所以装得下」只在换行密度低时成立——这是 ADR 0007 教训 1
（守卫必须建模运行时真正的容器）的**第四个实例**，这次错的是**单位**而非容器。

### 修法：三选一，选了「在正确的层面止损」

| | 方案 | 裁决 |
|---|---|---|
| (a) | 渲染层**截断并留可见标记** | ✅ **采纳** |
| (b) | 加载期断言「最坏 excerpt 必装得下」 | ❌ 单独实施**算术上不可能** |
| (c) | 写入侧按渲染代价设界 | ❌ 为一个显示容器**永久销毁证据** |

**(b) 被算术否决**：按写者真实值域构造最坏 excerpt（`WORST_SOURCE_SEQS` 段 ×
`EXTRACT_EVENT_EXCERPT_CHARS`、最长 label、全换行）实测 **4825 存储字符 →
3226 渲染 token**，是 1820 预算的 **1.77 倍**。裸断言会在加载期直接抛错、
插件装不上。

**(c) 被 `ROLLUP_TRANSCRIPT_CHARS` 判例本身否决**：该判例管的是**代码自己
构造的 prompt**；这里的输入是**存储的审计记录本身**。要保证必定装下，写入侧
得把引文砍到约 2412 字符——**为了一个显示容器永久销毁证据，是 D3 的反转**，
且**修不了任何已写入的 excerpt**。

**(a) 是唯一在正确层面止损的**：字节在存储侧是对的，只有**这一个视图**太小，
所以损失应在渲染处发生，并且**可见地**发生。实测同一条 payload：

```
truncatedToBudget → 保留     渲染包 7483 字符（容器 8192）    成本 1820 tok ≤ 预算
携带可见标记 " […truncated to fit the recall budget]"
```

**(b) 仍然加了，但断言的是修复后能成立的不变量**：最坏 excerpt 必须**投递出
带标记的内容**，而非空。双向实测（主 agent 独立复核）：

```
还原后            : LOADED OK, worstQuotePacketChars = 7484
把标记置空后重建  : THREW AT LOAD → "renders WITHOUT a visible truncation mark"
```

> **守卫自己差点成为恒真守卫。** 执行 agent 最初写的
> `!packet.includes(TRUNCATION_MARK)` 是**恒真通过**的——`''.includes('')`
> 为真，把标记置空后守卫照样放行。**这正是 `tools.ts` 里 `N·F > N·R` 那个
> 恒假守卫判例的同型复发**，且发生在**记录着那个判例的同一个文件里**。
> 已改为先判非空，并把 `TRUNCATION_MARK` 标注为 `: string`——字面量类型会让
> 空值比较变成编译错误，**守卫就丧失失败能力**。

### 连带修正：`sourceOf` 不再复用 `RECALL_NO_MATCH`

同一句 `RECALL_NO_MATCH = 'No stored memories matched.'` 在 query 模式下正确，
在 `sourceOf` 模式下**永远是假话**——能走到 render 说明记忆已经找到了。

更隐蔽的后果：**`metrics.ts` 用这个字符串统计 recall 未命中率**，于是
`sourceOf` 的空结果被计入「recall 未命中」，**污染 ADR 0005 用来决定是否引入
向量检索的那个数字**。

新增 `SOURCE_NOT_SHOWN`，**`RECALL_NO_MATCH` 的字节一字未动**（实测
`SOURCE_NOT_SHOWN.startsWith(RECALL_NO_MATCH) === false`，故 `metrics.ts` 的
前缀匹配不再吃到 `sourceOf` 的空结果，历史序列仍可比）。新文案**区分两种
成因**：引文过大 vs 会话取不到。

同批订正 `service.ts` 那句 `// cited, but the conversation has aged out of
retention`——对「L0 在别的库、`readableStores` 够不着」的情形**它是假的**
（实测 global 库有若干条属此类），而且因豁免子句的存在，**老化反而是较罕见的
分支**。两者在该处不可区分，故改为如实报告析取。

## 四、已登记的取舍：引文的信任标注是**整条**的，不是**逐段**的

QA 实测：**127/322 = 39.4%** 的引文条目，其 `title`（= 记忆的 provenance）
**低于**它所含某些段落的真实信任。活例：

```
BEFORE: - [user]  (id seq 2)  human:       这个仓库统一用 pnpm…
AFTER : - [quote] (id seq -1) tool-output: [user] 这个仓库统一用 pnpm…
```

同一行里 `[user]` 前缀与 `tool-output` 标签**互相矛盾**。

**方向是 fail-closed**（实测 **over-trust = 0**，从不把工具字节标成 `human`），
故**不是安全漏洞**，但对一个审计工具是**语义倒退**。

**决定：登记，不修。** 二者回答的是**不同问题**——`title` 是**整条 excerpt
作为一个对象**的信任下界（可据以行动的层级，由 `provenanceFor` 取最低信任
算出），`[label]` 前缀说明**每段**来源，两者都为真。唯一能让 `title` 变成
逐段的修法就是按 `\n---\n` 切分，而 §2.1 已实测否决。**这是标注伪影，不是
信任失效。**

## 五、为什么测试全绿——三个变异实验

修复轮之前，**216 个测试对以下三处破坏全部保持绿色**：

| 变异 | 结果 | 说明 |
|---|---|---|
| 读路径 `cited.excerpt.slice(0, 200)`（静默截断） | **216 全绿** | 全部 fixture 的 excerpt ≤64 字符，长度维度**完全未覆盖**——而长度正是 §三缺陷所在的维度 |
| `tools.ts` 的 `kind: turn.label` 改成硬编码 `'fact'` | **216 全绿** | §2.2 的可分辨性在**送达模型的那一层**无守卫 |
| 撤掉渲染层截断（即 §三缺陷本身） | **216 全绿** | **没有任何测试让引文穿过 `renderFramed`** |

根因是同一个：**断言停在 `service.source()` 的出口**（`assert.equal(turns[0]
.text, excerpt)` 只断言「函数返回它自己读到的值」），而缺陷发生在**之后**的
`renderFramed`。**这是 ADR 0009 教训 1「量到最外面那把尺子」在测试上的同型
复发**——本文第一节刚用它诊断了产品缺陷，测试自己就犯了同一个错。

已补一个**工具层 + 长 excerpt + 穿过 `renderFramed`** 的测试（先断言 fixture
确实超预算，否则测了个寂寞），三个变异现各自变红。全部新测试**用真实写者**
（`captureTurn` → `runExtractJob`）造数据，**无手写 `INSERT INTO evidence`**
——ADR 0009 教训 7 已为此付过一次代价。

顺带改名一条误导性测试：`the QUOTE path is not row-budgeted` 证明的是「不受
`SOURCE_TURN_LIMIT` 约束」，读起来却像「不受任何预算约束」，而 **token 预算
恰恰仍约束它**——那正是 §三缺陷的藏身处。

## 六、顺带登记（本轮不处理）

- **`group.test.mjs` 18b 的假注释已修**：它声称覆盖 "every `sourceOf`
  transcript"，而**断言体从不调用 `sourceOf`**——改动前就是空头承诺，改动后
  更是事实错误。**这是 `tools.ts` 刚刚记录的「注释声称守住了、实际没有」判例
  的第二次发生**，且在同一轮里被发现。
- **`conversations.label` 无 `CHECK` 约束**（§2.2 边界）：加约束是一次 schema
  migration，应独立评估。
- **`renderEntry` 只缩进 `\n`，不处理孤立 `\r`**：既有问题；实测真实数据
  **lone CR = 0**（CRLF 6 条）。改它会移动**每一个** injection packet 的字节
  并触及加载期预算断言，收益为零。
- **有 excerpt 时用户失去取得周边会话上下文的途径**（QA 的 R-1）：真实取舍，
  但修法（返回引文＋窗口）会让 `sourceOf` 的预算模型从「一条 hit」变回「多条
  竞争」，**把刚修掉的悬崖以另一种形态请回来**。应先决定产品语义。
- **跨库 + 引文的组合无真实数据覆盖**（QA 的 R-4）：global 库现有 **0 条**
  带 excerpt 的证据行（personal 记忆都由用户手动 `propose` 写入）。一旦将来
  personal 记忆开始由 extract 写入，该路径将首次被走到。
- **`propose` 不写 excerpt，明确不做**（见 §七）。

## 七、明确「不做」：`propose` 补写 excerpt

ADR 0009 §五把它列为推荐方案的**三个前置必改项之一**。本轮查明它**做不干净**，
故登记为「已评估、明确不做」，以免下一轮被重新提出。

**结构性依据**：`captureTurn` **只**在 `agent/turn-stopping` 被调用（全仓唯一
调用点），而 `propose` 在 **turn 中途**执行。**因此当前 turn 的 L0 行必然
不存在。** 实测 79 条 `principal-explicit` 证据行：

```
该会话完全无 L0                  : 2
L0 存在，但无一行早于 propose 时刻 : 19
L0 存在且有早于 propose 的行      : 58     ← 但那是之前的 turn，不是这条记忆的依据
```

**⇒ 补写 excerpt 只剩一个来源：`agent.session.events`。而对它的转写器
`collectTurnEvents` 是全仓唯一实现，并承载 §2.4 fail-closed 归因**——在
`propose` 里再转写一次，就是 D7–D9 在**安全边界**上的又一实例（provenance
决定注入资格）。复用 `collectTurnEvents` 也不行：它会与 `captureTurn` 对同一
turn 产生**两份不一致的转写**（propose 之后的事件不在其中）。

且 `sourceSeqs` 无从确定——extract 路径的 seq 来自模型的显式引用，propose
路径**模型没有说它引用了哪几行**。

**该缺口由 §2.2 的回退标注承担诚实性**：无 excerpt 时返回会话窗口，且明确
标注它是上下文而非引文。

## 八、教训

1. **调研工具的默认读法会静默丢数据。** 真实库有未 checkpoint 的 WAL：只拷
   `.sqlite` 而不拷 `-wal`，`7048f15b…` 那个库的主文件**只有 4096 字节**，
   读出来是「**no such table: evidence**」——不是少几行，是整张表不存在。
   **这是 ADR 0009 教训 4（`node:zlib` 只解 zstd 第一帧，静默少给 99.95%
   数据）的第二个实例**，两者合并为一条通用教训：**每次调研必须先做一次
   全量对照**，并用 `VACUUM INTO` 而非文件拷贝。
2. **一条读路径上有几把尺子，就要量到最外面那一把——这条规矩要在每次改动后
   重做。** ADR 0009 立了它，ADR 0010 教训 2 说「相邻两轮，一轮立规矩一轮
   违反它」，而本轮**在同一轮里第三次踩到**：产品缺陷是量到 SQL 出口
   （§一），新引入的缺陷是量到 `service.source()` 出口（§三），测试盲区还是
   量到 `service.source()` 出口（§五）。**规矩写进 ADR 不等于下一次会被执行。**
3. **纠正一个口径错误时，最容易犯下另一个口径错误。** 本轮初稿把 excerpt 的
   **字符数**标成了**字节**（145.4 KB vs 实为 145.4 KiB 字符 / 192.5 KiB
   字节）。**这是 ADR 0009 教训 6 的第三次复发**，而它恰好发生在一份批评
   「量错尺子」的文档里。**结论（体积无害）不变且更强，但理由必须换。**
4. **结论正确不等于理由正确，而错误的理由会在下一次数据变化时失效。**
   §2.3 的删除决定从头到尾没变，但支撑它的理由被完全替换（「早死 60 天」→
   「差值是无穷」）。若不换，等 L0 保留期真的开始咬人时，那条理由会自动
   失效，而不变量不会。
5. **守卫必须依赖它声称要检查的那个东西。** §三那个
   `!packet.includes(TRUNCATION_MARK)` 在标记为空时**恒真通过**，与
   `tools.ts` 里 `N·F > N·R`（N 被约掉）**是同一个形状**，且写在**记录着那个
   判例的同一个文件里**。**判例写下来不足以防止它复发——要靠变异实验。**
6. **一个修复引入的失败模式，可能比它修的缺陷更坏。** 原缺陷给**错的上下文**，
   新缺陷给**主动误导的否定**并掩盖记忆的存在。**判断修复好坏不能只看它修好
   的那条路径，要问「它新开了哪条路径，那条路径最坏说什么话」。**
7. **三个方案里选最少的那个，往往不在给出的选项里。** 本轮方案是「拆分
   excerpt」，评审否决后给的替代是「加 schema 承载 seq」，而实测选中的是
   **两者都不做**——整体返回、不解析、零 schema。**「能不能不做这件事」要在
   每一层各问一次。**
8. **写者的界与读者的界必须用同一个单位。** §三的根因是写者按**存储字符**
   设界、读者按**渲染 token** 计价，而 `renderEntry` 的缩进使二者相差近 2 倍。
   **两个都对的界，其乘积仍可以是缺陷**——与 ADR 0010 教训 1（两条各自正确的
   规则，交互后是缺陷）同型。
