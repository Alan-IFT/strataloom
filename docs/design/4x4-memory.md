# 4×4 记忆架构：目标形态、当前差距与分期

> 状态：设计已定稿，实施分四期。进度见 [`../STATUS.md`](../STATUS.md)。
> 本文只讲 **4×4 本身**；权限、事务、注入安全等既有边界见
> [`plugin-architecture.md`](../../plugin-architecture.md)，本文不复述。

## 0. 两条正交的轴

4×4 是**两个独立维度**，不是 16 个格子：

- **层（L0–L3）= 粒度**。同一条知识在不同抽象层的形态，由 Pipeline 逐层生长。
- **类（4 类 Memory）= 用途**。回答的是不同问题，由内容语义决定。

一条 L1 原子必属某一类；一个 L2 场景块可跨类聚合。**层决定"多细"，
类决定"答什么问题"**——这条区分是后续所有取舍的依据。

## 1. 四层：保存什么

| 层 | 保存什么 | 主要用途 | 现状 |
|---|---|---|---|
| **L0 Conversation** | 原始对话与完整上下文 | 核对原话、时间、来源 | ✅ 完整 |
| **L1 Atom** | 事实、偏好、约束、事件 | 精确召回可执行信息 | ✅ 完整 |
| **L2 Scenario** | 围绕项目/场景组织的知识块 | 快速恢复一个工作场景 | ❌ 缺失（现为全库摘要） |
| **L3 Core/Persona** | 长期画像、稳定模式、高层认知 | 迅速进入用户与团队语境 | ❌ 缺失 |

### 当前实现与目标的差距

现有 `derived=1` 的 rollup **不是 L2，也不是 L3**：它是「注入超预算时把整个
可注入集压成一段」的应急产物，既不按场景组织，也不承载长期画像。它解决的是
**预算**问题，而 L2/L3 解决的是**语境恢复**问题。

> **历史教训（必须避免重蹈）**：v2.3 曾预设 L2/L3 两个派生粒度，因**从未定义
> 二者的语义差异**而在评审中被砍。本次补全的前提是先把边界定死（见下），
> 否则宁可不做。

### L2 / L3 的判定边界（本次定义）

| | L2 Scenario | L3 Core/Persona |
|---|---|---|
| **回答** | 「这个场景当时是怎么回事？」 | 「这个人/这个团队一贯怎样？」 |
| **作用域** | 单仓库内，一个主题 | **跨仓库**，全局一份 |
| **数量** | 每仓多个（每场景一块） | 每用户恰好一块 |
| **来源** | 同主题的 L1 原子聚类 | 长期稳定的 personal 偏好 + 反复出现的模式 |
| **失效** | 其成员 L1 变化即失效 | 仅在长期趋势变化时重建（低频） |
| **存储** | repo 库 | `global.sqlite` |

**场景如何切分**（已定：按会话主题自动聚类）：由 rollup 时的 LLM 归纳，
产出 `scenario_key`（稳定 slug，如 `auth-refactor`）。选它而非按子路径，
是因为跨模块的工作流场景无法用路径表达；代价是边界由模型判定，故：

- 聚类**只在重建时发生**，不在读路径（读仍是一条 SQL）；
- `scenario_key` 稳定性由「复用已有 key」的提示约束，并在重建后校验；
- 一个 L1 原子可属 0 或 1 个场景，**不允许多属**——多属会让失效语义变成图问题。

## 2. 四类 Memory：回答什么

| Memory | 回答的问题 | 典型内容 | 现状 |
|---|---|---|---|
| **Coding** | 哪些工程经验值得带入下一次任务？ | 已验证的修复、失败方案、设计依据、陷阱、非回归检查 | ❌ **缺失** |
| **Repo** | Agent 需要了解这个仓库的什么？ | 架构地图、模块职责、代码入口、Commit/PR/Issue 证据 | ✅ = `fact` |
| **Personal** | 应该如何与你沟通协作？ | 语言、语气、解释深度、结果呈现偏好 | ✅ = `preference` |
| **Procedure** | 这类任务该如何执行？ | 步骤、检查清单、前置条件、例外、验证要求 | ✅ = `procedure` |

### Coding 与 Repo 的边界（最易混淆，必须说清）

判据是**「换个仓库还成立吗」**：

- 「本仓的构建入口是 `make all`」→ **Repo**（换仓即失效）
- 「`node:sqlite` 的 WAL 切换不受 `busy_timeout` 保护，需先设 pragma」→
  **Coding**（换仓仍成立，是可迁移的工程经验）

Coding 因此**默认 personal scope（跨仓可见）**，而 Repo 恒在 repo 库。
这也解释了为何 Coding 不能靠 `fact` 凑合：二者的**存储归属与失效条件都不同**。

### 存储归属（已定）

| 类 | 存储 | 可否投影到 `.repo_memory/` |
|---|---|---|
| Repo | repo 库 | ✅ 经人工审批 |
| Procedure | repo 库 | ✅ 经人工审批 |
| Coding | `global.sqlite`（跨仓） | ✅ 经人工审批（团队值得共享的经验） |
| Personal | `global.sqlite` | ❌ **永不投影** |

> **与原始设计的一处有意偏离**：原设计称「Personal 和 Procedure 保存在
> `.repo_memory/` 下」。实现改为：`.repo_memory/` 是**纯输出投影**（删了重写、
> 从不读回），且 Personal 永不投影。理由有二——个人偏好（语气/语言/深度）
> 提交进团队仓库会泄露个人习惯；且一个人人可编辑的文件若能成为记忆输入，
> 就绕过了 D1 身份边界。已确认采纳。详见
> [`../decisions/0001-repo-memory-is-projection-only.md`](../decisions/0001-repo-memory-is-projection-only.md)。

## 3. 分层召回

**目标**：平时用 L2/L3 快速进入语境，需要具体事实时回到 L1/L0。

```
注入（无查询串）          L3 画像 → L2 当前场景 → L1 补足余额
memory_recall（有查询串） L1 为主（FTS）→ sourceOf 回 L0
```

注入的分层是**预算分配**，不是检索：三层各有配额，L3 恒占少量（画像短），
L2 取当前最相关的 1 块，余额留给 L1。当 L2/L3 不存在时退化为今天的行为。

**检索融合（阶段 4）**：现为 FTS5（其 `rank` 即 BM25）。向量检索与 RRF 融合
在既有规范中处于**拒绝清单**（需引入 embedding 依赖，收益无人测量）。
本次将其改为**阶段 4 的待验证项**而非永久拒绝——但落地前置条件是：
先用 §9 metrics 采集「召回未命中率」，**有数据再做**。

三限（条数 / 字符预算 / 超时）已实现，各层配额沿用同一套预算机制。

## 4. 写入语义（原设计要求，逐条对照）

| 要求 | 现状 | 缺口 |
|---|---|---|
| 语义相同不重复写入 | `querySimilarRows` 回吐近重复，模型用 `replaces` 收敛 | — |
| 长期有效的补充/冲突规则更新匹配项，彻底移除被替代文字 | reconcile 分 kind 裁决；`forget` 清空 title/body | — |
| 适用环境失效时先修正范围，整条过时才删 | ⚠️ 无「修正范围」的中间态 | 阶段 1 一并考虑 |
| 用户点名忘记时只删该项 | `memory_forget` 按 id | — |
| 一次性任务指令不改写已保存记忆 | 入队闸 + reconcile 判定 | — |
| **是否长期有效不清楚时先询问** | ❌ 未实现（静默存下） | 阶段 1 |

## 5. 分期

每期**独立可交付、可回滚**，且不破坏既有不变量（D1–D9）。

### 阶段 1 · Coding Memory ＋ 澄清询问
- `MEMORY_KINDS` 增 `coding`；schema v6 扩 CHECK；工具描述给出与 `fact` 的判据。
- Coding 默认落 `global.sqlite`（跨仓），可被投影。
- 不确定是否长期有效时，通过既有 `ask` 能力询问而非静默存。
- **验收**：换仓后 coding 记忆仍可召回；`fact`/`coding` 在 recall 中可分别过滤。

### 阶段 2 · L2 Scenario
- schema v7：`memories` 增 `scenario_key`；rollup job 产出按场景分块的派生行。
- 失效沿用 D9 触发器（成员变则整块失效），**不新增失效协议**。
- **验收**：一个场景的 L1 全部 dormant 后其 L2 块消失；注入优先给当前场景块。

### 阶段 3 · L3 Core/Persona
- `global.sqlite` 中恰一条 `derived` 画像行，低频重建（非每次写入）。
- **验收**：新仓库首次会话即带上画像；画像不随单条偏好抖动。

### 阶段 4 · 检索融合（需数据支撑）
- 前置：metrics 显示召回未命中率显著。
- 届时评估 embedding 依赖是否值得，再决定 RRF。

## 6. 贯穿全程的不变量

补全 4×4 **不得**削弱既有边界：

- **D1** 身份/权限/scope 只从平台事实派生——新增 kind 不改变谁能写。
- **D7** 注入 packet 恒以 prompt 变量值投递。
- **D8** 存储内容变成模型可见文本只有一个函数——L2/L3 块同样走它。
- **D9** 派生失效由数据承担——L2/L3 沿用同一套触发器，**不得**新增
  「记得调用失效」的代码路径。

> 本项目已有三次「一条规则写在两处就漂移」的事故（D7–D9 的由来）。
> 每新增一层，先问：**这条规则会不会在第二个地方被复述？**
