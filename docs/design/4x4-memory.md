# 4×4 记忆架构：目标形态、当前差距与分期

> 状态：设计已定稿，实施分四期。进度见 [`../STATUS.md`](../STATUS.md)。
> 本文只讲 **4×4 本身**；权限、事务、注入安全等既有边界见
> [`plugin-architecture.md`](../../plugin-architecture.md)，本文不复述。

## D10 · 4×4 是插件的基底，不得删减

**四层（L0/L1/L2/L3）与四类（Coding/Repo/Personal/Procedure）全部为必需项。**
本项目奉行「少即是多」，但那条原则约束的是**实现机制**，不是**能力集合**：

- ✅ 允许：用更少的机制达成同一层/类（例：L2/L3 靠加宽 `derived` 承载，
  不新增列——机制变少，能力不变）；
- ❌ 禁止：因为「暂时用不上」「机制复杂」而删掉某一层或某一类，或把它降级为
  可选、待定、无限期延后。

差距只能通过**实现**关闭，不能通过**改小目标**关闭。若某项确实做不下去，
不得静默降级——必须新开一条 ADR，写明受阻的具体条件，并在
[`../STATUS.md`](../STATUS.md) 标注为受阻，保留在目标形态中。

> 历史教训：v2.3 的 L2/L3 曾被整体砍掉。砍它的**正当理由**是"两个派生粒度的
> 语义差异从未定义"——即**当时无法判定**，而不是"不需要"。本文 §1 已给出可
> 判定的边界（作用域 / 数量 / 失效条件），该理由不再成立，故必须补齐。
> 参见 [`../decisions/0002-l2-l3-need-defined-boundaries.md`](../decisions/0002-l2-l3-need-defined-boundaries.md)。

## 0. 两条正交的轴

4×4 是**两个独立维度**，不是 16 个格子：

- **层（L0–L3）= 粒度**。同一条知识在不同抽象层的形态，由 Pipeline 逐层生长。
- **类（4 类 Memory）= 用途**。回答的是不同问题，由内容语义决定。

一条 L1 原子必属某一类；一个 L2 场景块可跨类聚合。**层决定"多细"，
类决定"答什么问题"**——这条区分是后续所有取舍的依据。

## 1. 四层：保存什么

| 层 | 保存什么 | 主要用途 | 现状 |
|---|---|---|---|
| **L0 Conversation** | 原始对话与完整上下文 | 核对原话、时间、来源 | ✅ 完整 |
| **L1 Atom** | 事实、偏好、约束、事件 | 精确召回可执行信息 | ✅ 完整 |
| **L2 Scenario** | 围绕项目/场景组织的知识块 | 快速恢复一个工作场景 | ✅ `derived = 2` |
| **L3 Core/Persona** | 长期画像、稳定模式、高层认知 | 迅速进入用户与团队语境 | ✅ `derived = 3` |

### 当前实现与目标的差距

现有 `derived=1` 的 rollup **不是 L2，也不是 L3**：它是「注入超预算时把整个
可注入集压成一段」的应急产物，既不按场景组织，也不承载长期画像。它解决的是
**预算**问题，而 L2/L3 解决的是**语境恢复**问题。

> **历史教训（必须避免重蹈）**：v2.3 曾预设 L2/L3 两个派生粒度，因**从未定义
> 二者的语义差异**而在评审中被砍。本次补全的前提是先把边界定死（见下），
> 否则宁可不做。

### L2 / L3 的判定边界（本次定义）

| | L2 Scenario | L3 Core/Persona |
|---|---|---|
| **回答** | 「这个场景当时是怎么回事？」 | 「这个人/这个团队一贯怎样？」 |
| **作用域** | 单仓库内，一个主题 | **跨仓库**，全局一份 |
| **数量** | 每仓多个（每场景一块） | 每用户恰好一块 |
| **来源** | 同主题的 L1 原子聚类 | 长期稳定的 personal 偏好 + 反复出现的模式 |
| **失效** | 其成员 L1 变化即失效 | 仅在长期趋势变化时重建（低频） |
| **存储** | repo 库 | `global.sqlite` |

**场景如何切分**（已定：按会话主题自动聚类）：由 rollup 时的 LLM 归纳。
选它而非按子路径，是因为跨模块的工作流场景无法用路径表达；代价是边界由
模型判定，故：

- 聚类**只在重建时发生**，不在读路径（读仍是一条 SQL）；
- 一个 L1 原子可属 0 或 1 个场景，**不允许多属**——多属会让失效语义变成图问题。

### 承载方式：加宽 `derived`，不新增列

L0–L3 **不需要新的层级机制**。rollup 今天已经是 `memories` 表的普通行，
只靠 `derived` 标记；L2/L3 是同一回事，只是派生物的种类不同。故把
`derived` 从布尔**加宽为层级**：

```
derived  0 = 原始记忆（L1）   1 = 全库摘要   2 = 场景块（L2）   3 = 画像（L3）
```

这样做的收益是**改动面几乎为零**（已实测）：

- 现有 11 处消费者中有 10 处问的是「是不是原始记忆」，写作 `derived = 0`,
  **一字不改**仍然正确；
- **D9 的三个触发器**（`WHEN OLD/NEW.derived = 0`）同样一字不改，L2/L3 自动
  继承失效语义——这正是 D9「规则写在数据上」的红利；
- 只有「取哪一种派生物」的那一处需要指明层级。

对照被否决的方案：另加一个 `scenario_key` 列，等于**同一个概念（这行是什么）
用两个字段表达**，两者必然出现「`derived=1` 却带 scenario_key」这类无意义组合，
又要加约束去禁止它。加宽既有列则让这些组合**不可表示**。

场景**身份**同样不需要新列：场景块的 `title` 即其名（如
`Working set: auth refactor`），与今天 rollup 的标题用法一致。只有当出现
「必须按 key 精确定位某场景」的需求时才引入标识列——目前没有这个需求。

## 2. 四类 Memory：回答什么

| Memory | 回答的问题 | 典型内容 | 现状 |
|---|---|---|---|
| **Coding** | 哪些工程经验值得带入下一次任务？ | 已验证的修复、失败方案、设计依据、陷阱、非回归检查 | ✅ = `coding` |
| **Repo** | Agent 需要了解这个仓库的什么？ | 架构地图、模块职责、代码入口、Commit/PR/Issue 证据 | ✅ = `fact` |
| **Personal** | 应该如何与你沟通协作？ | 语言、语气、解释深度、结果呈现偏好 | ✅ = `preference` |
| **Procedure** | 这类任务该如何执行？ | 步骤、检查清单、前置条件、例外、验证要求 | ✅ = `procedure` |

### Coding 与 Repo 的边界（最易混淆，必须说清）

判据是**「换个仓库还成立吗」**：

- 「本仓的构建入口是 `make all`」→ **Repo**（换仓即失效）
- 「`node:sqlite` 的 WAL 切换不受 `busy_timeout` 保护，需先设 pragma」→
  **Coding**（换仓仍成立，是可迁移的工程经验）

这也解释了为何 Coding 不能靠 `fact` 凑合：判据不同，召回时也应能分别过滤。

### 存储归属：**kind 与 scope 保持正交，不新增绑定**

`scope`（repo | personal）**已经**是与 `kind` 独立的参数，由调用者声明、
决定落哪个物理库。因此不为 Coding 规定「默认落 global 库」——那会把两个
正交维度绑死，而「换仓是否成立」本就是**逐条**判断的：多数工程经验跨仓成立
（`personal`），但「本仓这个陷阱只在我们这套构建下出现」同样合理（`repo`）。

规则仍只有一条，与今天完全相同：**scope 选库，库的 trigger 派生可见性**。

| 类 | 典型 scope | 可否投影到 `.repo_memory/` |
|---|---|---|
| Repo | `repo` | ✅ 经人工审批 |
| Procedure | `repo` | ✅ 经人工审批 |
| Coding | 多为 `personal`，按条判断 | ✅ 经人工审批 |
| Personal | `personal` | ❌ **永不投影** |

「典型 scope」是给模型的**判断提示**（写在工具描述里），不是代码里的默认值——
一旦写成代码默认值，就成了第二处规定存储归属的地方。

> **与原始设计的一处有意偏离**：原设计称「Personal 和 Procedure 保存在
> `.repo_memory/` 下」。实现改为：`.repo_memory/` 是**纯输出投影**（删了重写、
> 从不读回），且 Personal 永不投影。理由与代价见
> [`../decisions/0001-repo-memory-is-projection-only.md`](../decisions/0001-repo-memory-is-projection-only.md)。

## 3. 分层召回

**目标**：平时用 L2/L3 快速进入语境，需要具体事实时回到 L1/L0。

```
注入（无查询串）          L3 画像 → L2 当前场景 → L1 补足余额
memory_recall（有查询串） L1 为主（FTS）→ sourceOf 回 L0
```

注入的分层是**预算分配**，不是检索：三层各有配额，L3 恒占少量（画像短），
L2 取当前最相关的 1 块，余额留给 L1。当 L2/L3 不存在时退化为今天的行为。

**检索融合（阶段 4）**：现为 FTS5（其 `rank` 即 BM25）。向量检索与 RRF 融合
在既有规范中处于**拒绝清单**（需引入 embedding 依赖，收益无人测量）。
本次将其改为**阶段 4 的待验证项**而非永久拒绝——前置条件是先采集数据。

**采集已就位，但结论必须谨慎**（见
[`../decisions/0005-recall-miss-rate-is-a-screening-signal.md`](../decisions/0005-recall-miss-rate-is-a-screening-signal.md)）：
`recallMissRate` 已由 `metrics.ts` 从 L0 用一条 SQL 算出（零计数器）。但实测
表明，一次零命中**无法区分**「库里确实没有」(A)、「有但措辞没对上」(B)、
「随口一探」(C)，而**只有 B 支持引入 embedding**。故该指标定性为**筛查信号**：
高比率意味着「去读转写」，不是「加向量」；判定 B 的证据在 L0——
*未命中 → 改写查询 → 命中同一条*。

三限（条数 / 字符预算 / 超时）已实现，各层配额沿用同一套预算机制。

| 要求 | 现状 | 缺口 |

## 5. 分期

每期**独立可交付、可回滚**，且不破坏既有不变量（D1–D9）。

### 阶段 1 · Coding Memory ＋ 澄清询问 ✅ 已完成

- `coding` 及其判据入 `MEMORY_KIND_CRITERIA`；同轮**收紧了 `fact` 的判据**
  ——二者最易混淆，故各自点名对方并给出唯一测试：「换个仓库还成立吗」。
- **schema v6**：扩 kind CHECK。SQLite 只能靠**重建表**做到，而该表挂着 9 个
  触发器与 FTS 外部内容索引，且 `evidence.memory_id` 是 `ON DELETE CASCADE`
  ——实测：带外键约束直接 DROP 会**删光全部证据行**（D3 所保证的可审计来源）。
  故迁移期间关闭外键（该 pragma 在事务内无效，须在事务外切换），提交前用
  `foreign_key_check` 复验；触发器由**唯一定义** `createMemoryTriggers` 重建，
  不另抄一份。
- 引导段与 extract 提示词的 kind 列表改为**渲染**，不再手写散文。
- scope 未引入 kind→scope 绑定；澄清询问由引导实现、复用平台既有
  `ask_user_question`，**未新建机制**（见
  [`../decisions/0003-clarify-by-guidance-not-machinery.md`](../decisions/0003-clarify-by-guidance-not-machinery.md)）。
- **验收（已通过）**：`fact`/`coding` 可分别过滤；同一 kind 可落两种 scope；
  v5→v6 升级不丢证据/对话/触发器/FTS，且新 kind 可写、未知 kind 被拒。

### 阶段 2 · L2 Scenario ✅ 已完成

- **schema v7**：`derived` 由布尔加宽为层级（`LAYER` 常量集中命名），**未新增
  列、未新增表**。两处触发器语义随之从 `= 1` 改为 `!= RAW`——否则场景块会在
  原始集变化后**残留**，正是 D9 要消灭的遮蔽。
- **迁移复用**：v6 与 v7 都要重建表，故抽出唯一的 `rebuildMemories`——由调用方
  只传「本次改的那一列」。基线列定义是**最早那次重建（v6）**的形态，v7 以
  override 加宽；这条纪律由 v6→v7 测试守住（我最初写错成 RAW-only，被它抓出）。
- **rebuild job** 产出多个场景块（每块一行），提示词改为返回严格 JSON；
  空回复走重试出口而非提交，否则「零场景」会被误读为「预算够用了」。
- **注入**取全部派生行、按层级与新近度排序，交由既有预算裁剪。**刻意不做
  「挑当前场景」**：该路径无查询串（§4.1），相关性无法诚实计算；靠 cwd 或上次
  工具调用去猜，等于新增一条与 `memory_recall` 竞争的弱检索规则。实测预算内
  可容纳 5 块而上限为 6，此问题基本不存在。
- **验收（已通过）**：rebuild 产出多块场景且各为 `LAYER.SCENARIO`；注入以场景
  替代原始集且不超预算；一次原始层写入即清空**全部**派生层（继承 D9，零新增
  失效代码）；v6→v7 升级保留数据与九个触发器，非法层被拒。

### 阶段 3 · L3 Core/Persona ✅ 已完成

`global.sqlite` 中恰一条 `derived = 3` 画像行。schema **无需再改**：
`LAYER.PERSONA` 已被 v7 接受，D9 已覆盖全部层级。

**触发条件（已定，见 [`../decisions/0004-l3-rebuild-trigger.md`](../decisions/0004-l3-rebuild-trigger.md)）**
——动手前实测的三条事实改变了问题形状：

| 实测 | 后果 |
|---|---|
| D9 会在任何 personal 写入时删掉画像 | 与「不随单条偏好抖动」直接冲突 |
| 20 条偏好仅 440 tok（预算 1300） | **L2 的「预算溢出」触发器对 L3 不适用** |
| 原子 39 tok vs 画像 15 tok | L3 的价值**不在压缩**，而在可外推的人格判断 |

故触发条件是：**画像缺失，或模型判定其已过时**。在既有维护轮里对全局库问
一句「这份画像是否仍准确描述此人？」——不设阈值、不加计数器、不加列、不加
job kind。代码算不出「这个人变了」，那是语义判断；任何计数式代理指标与它
都无因果关系（与被否决的 trust 公式同形）。

**D9 保持不变**：画像被删后由下一轮重建；模型若判定未变，写回同一份，对
模型无感。为画像豁免 D9 需在触发器里引入「按 kind 分支」，把一条规则变成
带例外的规则——本项目刚用两轮代价消除这类复杂度。

**实现要点**：复用 `rebuild` job（**未加 job kind**），按 `store.kind` 分派——
repo 问「是否溢出」，global 问「画像是否过时」。`keep` 判定**不写库**，这既是
不抖动的保证，也让 D9 删除画像变得无害：下一轮写回同一份文本。画像恒一行，
`visibility` 恒 `private`（永不投影）。

- **验收（已通过）**：全新仓库首次会话即带画像，无 git 树的会话亦然；
  `keep` 时正文逐字未变且 revision 不推进；`rewrite` 替换而非累积；
  坏回复（缺 body / 未知 verdict）走重试出口；无 `llm` 时不入队，注入优雅
  退化为原子偏好。

### 阶段 4 · 检索融合（需数据支撑）
- **采集已完成**：`recallMissRate` / `recallCalls` 随每次维护轮记入结构化日志。
- **仍不可仅凭该数动手**：它混合了 A/B/C 三类（见 §3 与 ADR 0005）。开工的
  正当条件是——比率显著 **且** 抽读 L0 转写确认存在 B 类（改写后命中）的实例。
- 届时才评估 embedding 依赖是否值得，再决定 RRF。

## 6. 贯穿全程的不变量

补全 4×4 **不得**削弱既有边界：

- **D1** 身份/权限/scope 只从平台事实派生——新增 kind 不改变谁能写。
- **D7** 注入 packet 恒以 prompt 变量值投递。
- **D8** 存储内容变成模型可见文本只有一个函数——L2/L3 块同样走它。
- **D9** 派生失效由数据承担——L2/L3 沿用同一套触发器，**不得**新增
  「记得调用失效」的代码路径。
- **D10** 4×4 是基底，不得删减（见本文开头）。简化只针对机制，不针对能力。

> 本项目已有三次「一条规则写在两处就漂移」的事故（D7–D9 的由来）。
> 每新增一层，先问：**这条规则会不会在第二个地方被复述？**
>
> 而 D10 防的是相反方向的失误：**别把「机制该更少」误读成「能力可以更少」。**
> 两者一起用才对——用最少的机制，交付完整的 4×4。
